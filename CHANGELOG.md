# Changelog

All notable changes to the IronTrellis (formerly Continuity) packages are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); every publishable package shares one version (`scripts/check-versions.mjs` enforces it, for the npm packages, the MCP Registry entries and this file). The Python package is the exception: `check-versions` holds it at 1.0.0rc1 until it is ported to format 2. Findings quoted below are from the independent evaluation of Continuity dated 23 September 2026.

## [1.0.0-rc.2.1] — LangChain peer fix

1.0.0-rc.2 with one dependency fix. Nothing else changes: the history format, the commands, the hooks and the gateway are as in 1.0.0-rc.2, and everything the documentation says of 1.0.0-rc.2 applies to this release too. Published to npm under the `next` tag.

### Fixed

- Installing `@ramex-labs/irontrellis-agent-shims` together with `@ramex-labs/irontrellis-remote` or `@ramex-labs/irontrellis-remote-tools` gave an invalid dependency tree from 30 October 2026. That day LangChain released `@langchain/langgraph-sdk` 1.12.9, which agent-shims reaches through `@langchain/langgraph` and which needs `@langchain/core` 1.2.18 or later, while remote and remote-tools 1.0.0-rc.2 asked for exactly `@langchain/core` 1.2.12. npm warned and `npm ls` reported the tree as invalid; installs with strict peer checks refused it.
- remote and remote-tools now accept `@langchain/core` 1.2.18 or any later 1.x (the peer is still optional). The packages are tested with `@langchain/core` 1.3.2. LangSmith, which `@langchain/core` pulls in, is tested at 0.11.5.
- If you stay on 1.0.0-rc.2 for now, add `"overrides": { "@langchain/langgraph-sdk": "1.12.8" }` to your `package.json` and keep `@langchain/core` at 1.2.12.

### Release checks

- The install check (`scripts/verify-install.mjs`) accepts a peer range of the form `^X.Y.Z`. The consumer projects install the version the workspace tests with, and a new row installs the packed packages with the peer at the bottom of its range, X.Y.Z, against the registry as it is that day. It requires a clean `npm ls --all` and an import of every public subpath.

## [1.0.0-rc.2] — IronTrellis Core

IronTrellis Core: a new history format (format 2, `irontrellis-event/2`) and the commands, hooks and gateway that write it. Published to npm as a release candidate, under the `next` tag.

### Format 2

- Every new history is format 2 (SPEC-IRONTRELLIS-CORE-v2). Each line carries a record hash that chains to the one before it; the head is the last record hash.
- Publishing 1.0.0-rc.2 releases format 2. Histories written by 1.0.0-rc.2 keep their verdicts: later versions read them exactly as 1.0.0-rc.2 does, or refuse them, and rule fixes after 1.0.0-rc.2 come as a new format.
- A state root commits to the replayed state: every record the replay derives (agents, roles, grants, sessions, budgets, refusals, effects, counterparties, duties and the rest) is a leaf of one Merkle tree. Signed checkpoints (`STATE_CHECKPOINT`) and the pin's head attestation (`irontrellis-head-attestation/2`) name the state root and the projection head. A reader can resume from a snapshot; the root is recomputed from the snapshot's records every time and a mismatch falls back to a full replay.
- Budgets: amount, count and per-request caps over groups of actors, roles, actions and resources, per period, with optional rollover. Only admitted operations are charged.
- First-class records: refusals (`REQUEST_REFUSED`, re-derived by every replay for CORE and BUDGET refusals), effects (`EFFECT_RECORDED`), counterparty receipts (`COUNTERPARTY_RECEIPT_RECORDED`, signed by a registered counterparty) and signed intent declarations.
- Reconciliation observations (`RECONCILIATION_OBSERVED`, type 42). A reconciler records what a provider reported about a call, signed by its own session. The observation is matched to the decision it names, or recorded as unmatched. `recordObservation` on the runtime and execution handles writes it. The same provider event reported twice is refused (`OBSERVATION_DUPLICATE`), and `verify` lists conflicting reports.
- The investigation duty policy of Continuity 0.3 (activation, findings, contests and the duty view) is part of the engine.
- The export view (`irontrellis-export/2`) carries a range of events with the state at both ends; `verifyExportView` checks it without the rest of the history.
- A migrated history's genesis must state the source format's versions exactly as the source genesis does: `migratedFrom.versions` equal to `migratedFrom.genesis.versions`, key for key, or the genesis is refused (`EVENT_DATA_INVALID`). A history written by the migration tool always has them equal; a hand-edited copy no longer reads differently in different readers.
- Duty-policy events 29–31: a fenced outer session is SESSION_FENCED before the descriptor, event and finding literal fields are checked (A-202.1); the fields' shape, including the Identifier grammar, is still checked first.
- The engine-wide Identifier limit (an Identifier over 256 UTF-8 bytes in an event is `INVALID_INPUT`) has shared conformance vectors: 9 of the cases in `packages/core/test/fixtures/a202-boundary-vectors.json`, which the TypeScript engine and the zero-knowledge guest agree on. Before, only TypeScript unit tests pinned it.
- A rejected event leaves the replay state exactly as it was. Two rare refusals inside migrated histories used to leave a trace in memory (a late source time at the end of the migrated part, and a refused migrated genesis). Accepted histories, their roots and every refusal code are unchanged.

### Owner approval policies

- A format-2 history can require more than one owner key for control events. `ownerPolicy` (in the genesis or in an owner key rotation) sets a threshold, optional per-type thresholds, key classes and labels. Extra signatures go in `additionalControlAuthorizations`, and each must come from a different credential.
- A per-type threshold may be lower than the main one only for events that actually reduce power (revoking a permission, a fence, a termination, an unappointment, a counterparty retirement, a budget change that only tightens it) and checkpoints. A policy cannot ask for more signatures than its non-agent keys can give.
- Under a policy, a key rotation out of a committed epoch needs a proof of possession for every revealed key, and an owner key may not reuse a session or counterparty credential.
- API: `coOwnerKeys` and `ownerPolicy` on `createLocalOwner`, `prepareControlEvent` and `submitControlEvent`, `rotateOwnerPolicy` and `prepareOwnerPolicyRotation`. CLI: `owner rotate-key` and `owner commit-next-key` take `--owner-policy <file>` or `--reset-policy`, and `owner status` shows the policy.
- Built in this release: human attestation for PHL, Proof of Human Lineage (`humanFloor: "ATTESTED"`, `attesters`, `attestations`, with the key classes, lapse and the writer's expiry and horizon checks), the restoration rules for lapsed keys in replay, the committed next key as a rotation signer in replay (under `recovery`, which no shipped tool writes; see the next item), snapshot resume and export views under a policy, and policy checks in remote witnesses.
- Not built in this release: a writer for a recovery rotation (an owner key rotation authorized under `recovery` without a current owner key). Replay honors such a rotation exactly as the specification defines it, but the owner API and CLI offer no way to author one: `rotateOwnerKey` needs a current owner key, and `prepareControlEvent` refuses `nextKeyAuthorizations` and key-changing rotations. A deployment that sets `recovery` therefore has a rule replay would honor and no shipped tool to exercise it; recovering a lost quorum needs an external producer of the event, which this release neither ships nor documents. The writer is planned after this release ([known issue 24](docs/records/KNOWN-ISSUES-r2.5.md)). The handover, witness binding, the two-phase key rotation and `commitNextKey` are still signed by one key; under a policy that needs more, they refuse.
- Future work: how hook decisions charge count budgets, or a light `USAGE_CHARGED` event in a later format minor, is still an open decision. Until it is decided, only admitted intents charge budgets.

### Adapter storage

- `@ramex-labs/irontrellis/adapter` now works on format 2: `openConfiguredEventStore`, `stateOf`, `createHistoryTransfer` and `openCheckpointStorage`. A history can be sent to another host in segments; the receiver checks every chunk and both roots before it accepts the copy. Errors use six new `TRANSFER_*` codes.
- Limits: a transfer always starts at position 0, and a received history is limited to 512 MiB and 4,096 segments.

### Commands and connectors

- `irontrellis init` writes format 2 only (`--legacy` is gone). New commands: `budget declare|update|close|show|headroom`, `checkpoint create|list|verify`, `counterparty register|rotate|retire|receipts`, `duty describe|activate|dispose|contest|inspect`, `export --view|--from|--to [--records]` and `export verify`. `authorize --record-refusal` records a DENY signed by the actor's session. `status` and `verify` show the state root; `migrate --status` reports where a migration stands and the next step.
- Hooks: `irontrellis-hook init` writes format 2 and never sets `enforceFromReadOnlyHistory`; a tool call the history denies is recorded as a refusal (one the protective rules refuse is not). The hook has its own connector session for CONNECTOR refusals. Configs can pin the history with `historyId`.
- MCP gateway: the demo case is format 2 and has the gateway's own connector session; denials are recorded as refusals; an upstream's reports can be recorded as CONNECTOR refusals, effects and counterparty receipts (`records` per job or tool). `setup --investigation` adds an open investigation duty for the duty commands.
- Witness: registers and witnesses format-2 histories (`historyId` = the first record hash). Witness head statements are unchanged (`irontrellis-head-statement/1`).
- MCP SDK: both MCP packages move from `@modelcontextprotocol/sdk` 1.30.1 (and `zod`) to `@modelcontextprotocol/server` and `@modelcontextprotocol/client` 2.2.0, pinned exactly (with `@modelcontextprotocol/core` 2.2.0, which both pin). 2.2.0 fixes GHSA-6qxp-vccf-f47h, where the 2.0 and 2.1 OAuth client could send credentials to an authorization server chosen by the MCP server. IronTrellis's MCP client connects over stdio without OAuth, so it never ran that code. `pnpm audit` no longer reports it. The stdio servers answer clients at protocol revision 2026-07-28 and 2025-era clients with the same tools, schemas, structured replies and refusals. A gateway upstream may set `"protocol": "2026-07-28"` (that revision exactly) or `"legacy"` (the default, unchanged).
- CLI: a flag before the command keeps its own value. `irontrellis --json status false` is now a usage error, answered as JSON; it used to print the human-readable status with exit 0, because removing the command words let `--json` take the `false` that followed them. Found by the fuzzer.
- Conformance adapters (`conformance/adapters/node.mjs` and `reference-node.mjs`): a request line ends at `\n` only, and one trailing `\r` is dropped. U+2028, U+2029 and a lone `\r` no longer cut a request in two, which used to give two error answers and pair every later answer with the wrong request. The Python adapter already read lines this way. The frozen legacy adapter (`conformance/legacy/adapters/node.mjs`) is unchanged ([known issue 73](docs/records/KNOWN-ISSUES-r2.5.md)). Found by the fuzzer.
- Core: a position or time of `-0` is no longer taken as `0`. Head attestations, anchor log entries and owner-key epochs need a canonical U53, as canonical encoding defines it. `verifyHeadAttestationFacts` gave `prefix: true` for a head position of `-0`; the Python verifier's `prefix: false` was the correct answer. The verdict was `valid: false` either way. The Python conformance adapter now reads request JSON as `JSON.parse` does, so `-0` stays negative zero there too. Found by the fuzzer.
- MCP gateway and evidence server: the stdio bounds are rates, not lifetime totals. The agent's input and each upstream's output allow at most 1,024 messages within any 60 seconds (per-frame and buffer bounds unchanged); before this, the 1,025th message of a session ended the gateway, and the 1,025th upstream frame left that upstream unusable. A closed upstream connection is now dropped, so the next governed call reconnects and checks the tool definition again; a call whose reply was lost stays `OUTCOME_UNKNOWN` and is never re-sent.
- New package, `@ramex-labs/irontrellis-anchor-outbox`: it publishes commitments to a history on a public chain. It checks each anchor statement against the actual history, then drives one transaction for it through the installer's own signer and node, with one signer call and one first send per attempt; after a crash it reconciles instead of sending again. Its anchor check produces no verification report (see "Not established").
- Anchor outbox: reconciliation compares a transaction's signature values `r` and `s` by value. A node may report each as a 32-byte word or as a canonical QUANTITY, and the signed bytes still bind them exactly. Before this fix, a correct transaction whose `r` or `s` began with a zero byte (about 1 in 85) was reconciled as a CONFLICT and halted the outbox. A node that reports `r` and `s` as quantities left about one transaction in six INCOMPLETE.

### Security

- Hooks: the protective rules now cover Codex's and Cursor's configuration as well as Claude Code's: the project's `.codex/` and `.cursor/` trees, `config.toml` and `hooks.json` in `CODEX_HOME` (else `~/.codex`), and `~/.cursor/hooks.json`. Before this, an agent under Codex or Cursor that could run shell commands or write files could turn its own hooks off for later sessions (`[features] hooks = false`) or empty the hook entries, and the guard allowed it. Reads, and a project's own `config.toml` or `hooks.json` elsewhere, stay allowed.
- MCP gateway: access is checked again after the attempt record is written to disk and synced, just before the upstream tool is called. Before this fix, a revocation or expiry that landed while the attempt was being synced could still reach the upstream tool. Now the call stops there. The attempt was already admitted, so it reports `OUTCOME_UNKNOWN`, and a repeat reconciles it without calling the upstream. This covers exactly-once jobs and recorded per-call tools.
- Format 2 as released means session-challenge profile g3. The `frozen-r2.3` profile (`IRONTRELLIS_CHALLENGE_PROFILE=frozen-r2.3` or `setChallengeProfile`) only verifies the frozen conformance vectors in `conformance/v2`: under it, every format-2 write is refused with `CHALLENGE_PROFILE_READ_ONLY` and nothing is written, so IronTrellis writes format 2 under g3 only.

### Remote tools, managed agents and the gateway's HTTP and cooperative modes

New packages, all on format 2:

- `@ramex-labs/irontrellis-remote`: the SDK for cooperative remote tools. It has five imports: `.`, `./langchain`, and `./local`, `./runtime` and `./attempts`, which re-export Core. It is built on `@ramex-labs/irontrellis-remote-tools`.
- `@ramex-labs/irontrellis-remote-tools`: the cooperative destination, executor, durable state and recovery.
  - The destination is pinned to one history and authorization domain. It accepts only verified transfers of a format-2 export view. By default (`REQUIRE_OWNER`), each one must extend the history it accepted before at an owner-authenticated head. Under that default the executor completes a call only when its handle signs with the owner key; with a session-only handle every run ends `OUTCOME_UNKNOWN` with nothing dispatched. Set the destination to `COORDINATOR_AUTHENTICATED`, or give the executor the owner signer, which puts the owner key in its process ([known issue 78](docs/records/KNOWN-ISSUES-r2.5.md)).
  - A lost reply leaves the outcome unknown, and recovery looks up the status or cancels; it never sends the request again.
  - `./langchain` wraps the tools for LangChain. It needs the optional peers `@langchain/core` 1.2.12 and `zod` 4.6.5.
- `@ramex-labs/irontrellis-managed-agents`: a backend adapter for managed agents.
  - `decide` is advisory and writes nothing.
  - `record` admits the exact intent in the history before any handler runs, waits for the host's finality check outside the writer lock, then rechecks authority and fencing before it enters the fixed handler.
  - `reconcile` writes what a provider reported as `RECONCILIATION_OBSERVED` (type 42) observations. Type 42 replaces the separate signed findings ledger; old ledgers are not imported.
- `@ramex-labs/irontrellis-agent-shims`: approval and resume bindings for the OpenAI Agents SDK (0.20.0) and LangGraph (1.4.21) on top of managed-agents. An approval, or a resumed checkpoint, is never permission to run: authority is checked again before the record.
- MCP gateway, four new subpaths:
  - `./http`: an authenticated loopback HTTP entrance, plus a router and a private mTLS backend that each check the bearer token, resource and binding on their own;
  - `./cooperative`: cooperative tasks that keep their original business identity, with cancellation authorized separately;
  - `./tasks`: the MCP Tasks extension over cooperative work;
  - `./access-http`: bearer-token verification with `jose` 6.2.12.

  The gateway now depends on `@ramex-labs/irontrellis-remote` and `jose`. Public HTTPS deployment is not part of this release.
- Examples (private, not published), under `integrations/`:
  - `policy-composition`: Cedar and OpenFGA policies added on top of the Core decision. Both must allow, and neither can override a Core denial.
  - `langchain-evidence`: a LangChain agent that reaches the protected evidence MCP server through real framework dispatch.
  - `protected-evidence-mcp`: the evidence MCP server those two use.
- The workspace holds `langsmith`, which LangChain pulls in, at 0.9.0. The type declarations of 0.10.10 and 0.10.11 fail a strict type check.

Removed from the remote API, compared with Continuity's preview remote packages:

- `checkpoint(events)` (sending raw events inline) and `migrateDestinationHistory` are gone. Use `checkpointHistory(store)`, which sends a verified format-2 export view. Old segmented destination directories and `historyBinding` profiles are not accepted.
- A reviewed migration of old Continuity destination state into format 2 is still to do. Until then there is no migration path for it.

### Read only

- Legacy (`continuity-event/0.2`) and format-1 (`irontrellis-event/1`) histories open read only: questions and `verify` work, writes are refused with `FORMAT_READ_ONLY` (reason `LEGACY` or `FORMAT_1`). A hook or gateway keeps enforcing from a never-migrated older file only when its config says `"enforceFromReadOnlyHistory": true`, with a warning on every open.
- The public API writes format 2 only: `createLocalOwner({ format })` and every handle built from owner options refuse another format with `INVALID_INPUT`, and the public store refuses `readOnlyFormats: false` and older genesis formats. The legacy and format-1 writers remain as test tooling in the non-public `@ramex-labs/irontrellis/internal-format1`.
- Enforcement from an opted-in older file is read-only and fails closed: the hook admits no session there (tool calls are refused) and the gateway refuses a call that must be recorded before dispatch (`FORMAT_READ_ONLY` with a `remedy`). Before this, both wrote session admissions and call records into the older file. Run `irontrellis migrate` to write.

### The Claude Code plugin

- A Claude Code plugin (`plugins/irontrellis/`, marketplace `irontrellis`) runs the same guard as `irontrellis-hook install claude-code --write`, on macOS and Linux (on Windows, use the hook route). Choose one route per project: the plugin steps aside where it finds the exact hook entries install writes, and the hook says so when a session starts.
- Neither route looks the guard up on PATH. `install claude-code --write` now writes `/bin/sh -c '<wrapper>' <node> <launcher> claude-code <Event>` by absolute path, the wrapper refusing a tool call when the node or the launcher is missing or the guard fails (earlier `irontrellis-hook` entries and wrappers are rewritten). The plugin runs `/bin/sh launch.sh`, which runs the node and launcher recorded by `irontrellis-hook pin-runtime` (and by every `init`) in `~/.irontrellis/plugin-runtime`, and refuses tool calls when they are missing. Codex and Cursor installs keep `irontrellis-hook` for now.
- In a project without IronTrellis, the plugin tells the user when a session starts (and when it is resumed or cleared, not after a compaction) and asks for a choice, which only the user makes: typed in Claude Code with the `!` prefix, or in the user's own terminal. `irontrellis-hook choose 1` declines, `choose 2` sets IronTrellis up (`init --agent claude-code`, the plugin route; its next steps leave out the hook route's `install`) and `choose 3` picks the hook route; the long forms (`choose --decline`, `init`, `choose --use-hook`) work too. The notice also says that leaving without a choice brings it back next time (`/exit` gives Claude no turn to say so). `choose --status` shows it and `choose --reset` undoes it. The choice is stored per user in `~/.irontrellis/route-choices.json` and applies only to a project without IronTrellis. Until a choice is made, Claude Code's own permission rules apply. The agent's own `choose`, `init` or `pin-runtime` is refused with the installation policy in plain words and the `!` command to run instead.
- The `irontrellis` command takes `--no-color` and honors `FORCE_COLOR` (any value but `0` or `false` gives color without a terminal); `NO_COLOR` with any value, empty too, still turns color off.
- `irontrellis-hook statusline` prints one line for Claude Code's `statusLine` setting (guarded by the plugin or the hook route, not set up, or declined); the user adds it to their own settings. For a session the guard did not admit at its start, such as the one in which `choose 2` set the project up, it says "guarded from the next session" (the guard refuses that session's tool calls until a new one starts).
- `irontrellis-hook init` and `choose 2` print a few plain lines: what is set up, where the history and keys are (the home directory as `~`), each warning in one sentence with a pointer to `irontrellis doctor`, the next steps and what to publish. `--verbose` prints every step and the full warnings, which `--json` also carries (`warnings`, and `notes` for the short forms). A plain `init --agent claude-code` where the IronTrellis plugin is enabled says it is on the plugin route and leaves out the hook route's `install`, unless the hook route was chosen. In both inits' "A reader checks them with" command, the history path is quoted when the shell needs it.
- A refusal's text follows the brand's voice (BRAND-001): "IronTrellis · DENY:", the plain fact, then the code and detail in parentheses (it was "IronTrellis DENY <code>: …"), on both routes and for a guard that cannot check a call (exit 2); ALLOW and INDETERMINATE reasons read "IronTrellis · ALLOW:" and "IronTrellis · INDETERMINATE:". The plugin has an icon (the brand badge). The plugin's own skill, `irontrellis:irontrellis-handover`, now runs without asking the user. A settings hook that is not install's entry, with the plugin enabled too, says that both routes run the guard.
- The Claude Code PreToolUse entry, in the plugin's hooks file and in what `install claude-code --write` writes, sets `"onFailure": "block"`: a guard that times out, cannot start or exits with another code refuses the call (Claude Code 2.1.309 honors it; 2.1.100, 2.1.200 and 2.1.250 load the file with it). `install` updates an existing entry to it, and the verified hook route requires it. If you installed the hook route with an earlier build, run `irontrellis-hook install claude-code --write` again: until then the plugin does not count that entry as the hook route.
- Claude Code refusals exit 2: a denied tool call prints the "IronTrellis · DENY: …" reason on stderr, with nothing on stdout, on both routes (the plugin and the settings hook). The reason starts with a newline, so it stands on its own line under the label Claude Code puts in front of an exit-2 error (its hook command in square brackets). Asks, allows and deferrals stay JSON at exit 0. Codex and Cursor are unchanged.
- `irontrellis verify` and `export verify` take `--expect-history-id <0x…>` and `--expect-owner-key <0x…>` (repeatable) or `--expect-owner-keys <file>`: the history id and the first owner keys the history's owner published, checked before anything else. A different history, such as a substitute re-signed under other keys, is refused with `HISTORY_ID_MISMATCH` or `OWNER_KEYS_MISMATCH` (expected and found values in `identity`). Without them, the report shows the id and keys it read from the file and says they are not confirmed. A file that, between the identity read and the verification, becomes another history or loses the verified head from its chain is refused with `HISTORY_CHANGED` (events appended to the same history are not). The key set is compared as a set; the Python verifier and the programming interface do not have the option yet. `irontrellis init` and `irontrellis-hook init` end with these values under "Publish these" (and `publish` in `--json`).
- In the `irontrellis` command's output, the state colors paint only the four state words (ALLOW, DENY, INDETERMINATE, OPEN); other emphasis is bold. The Forge color marks the product name in the header only, once per view.
- In a guarded project the agent cannot change Claude Code's own configuration: the settings files (whole), any `.claude.json` or `.mcp.json`, every `.claude/` folder (nested ones and the user's `~/.claude/`, Claude Code's `projects/`, `plans/` and `todos/` excepted), the plugin and the plugin cache, the installed IronTrellis packages, and the node and launcher the guard runs with; nor move or delete a folder holding them or the history, nor run `git clean` or `git stash -u`. A shell command naming them may only read them, and extracting, patching or checking out into a folder holding them is refused; package-manager commands that could replace the guard or its node are refused (through runners such as `nice`, `timeout` and `sh -c` too). Paths are compared through symlinks; settings and config files that are not regular files (a FIFO) are refused, not read. Shell-command matching is best effort.
- Codex (from a live check of the Codex route, 23 October 2026): `init --agent codex` and `irontrellis doctor` warn when a Codex config turns hooks off (`[features] hooks = false`); `install codex` gives PreToolUse a 120-second timeout, since Codex has no setting that makes a timed-out hook refuse; the refusal of `choose`, `init` and `pin-runtime` under Codex and Cursor says to run it in your own terminal (the `!` prefix is Claude Code's); the hooks README describes Codex's one-time folder trust and `/hooks` review.
- Fixes from an independent review, 23 October 2026: a path through a symlink and then `..` is checked where the file system takes it, for file tools and shell commands alike (it was collapsed as text first, so `link/../x` could reach the configuration); `checkpoint create`, `budget declare|update|close`, `counterparty register|rotate|retire`, `duty activate|dispose|contest` and `verify --accept-rollback` are refused as writing commands; the protective rules decide before the history is opened, so with `"failOpen": true` a history that cannot be read no longer lets a protected call through; `irontrellis-hook statusline` says "set up, but not guarded" when Claude Code's `disableAllHooks` is on; in a project not set up, a relative path to the choice file or the runtime pin is resolved from the agent's working directory.
- A session admitted under a guarded route whose config later vanishes or changes is refused, not treated as unconfigured. The route's project (`CLAUDE_PROJECT_DIR`) is protected as well as the config's.
- `init --allow` refuses, before writing anything, a project path too long for a grant's resource (128 characters, or 256 bytes in UTF-8).
- With `"failOpen": true` (off by default) a Claude Code tool call the guard cannot check (an unreadable event, a missing history, a replay error) is answered with exit 0 and a visible warning, so it reaches Claude Code's own permissions; a guard that cannot start still refuses. failOpen is read from the config the session was admitted under, never from the event's working directory.
- Two copies of the guard on the same events (both routes, or the hook installed twice) admit a session once, record one refusal per tool call and write one handover per stop. `irontrellis doctor` recognizes the plugin route and flags both routes installed together, and any hook entry that only looks like IronTrellis's.

### Breaking (test hooks removed from public subpaths)

Three test hooks and three internal functions of 1.0.0-rc.1 relax a write guard, touch signing or the witness record, or take unchecked input, so they are no longer on a public subpath. They remain in the source modules for this repository's own tests and tools, which import those files directly; they are not part of any public API.

- `setCapacityLimitsForTests` (was on `@ramex-labs/irontrellis`): it can raise the format-2 hard limits. Internal: `packages/core/src/capacity.ts` (built: `dist/capacity.js`).
- `setAgentConnectorForTests` (was on `@ramex-labs/irontrellis/custody`): it replaces the connection the ssh-agent signer uses. Internal: `packages/core/src/custody/ssh-agent.ts`.
- `resetRefusalRateLimitsForTests` (was on `@ramex-labs/irontrellis` and `@ramex-labs/irontrellis/local`): it clears the per-actor refusal rate limit. Internal: `packages/core/src/session-writes.ts`.

- `witnessSessionOf` (was on `@ramex-labs/irontrellis/store` through a re-export): it can change the persisted witness side file. Internal: `packages/core/src/store.ts`.
- `signedTransition` and `sessionOf` (were on `@ramex-labs/irontrellis/runtime`): they take an unchecked owner configuration. Internal: `packages/core/src/runtime-writes.ts`.

The exported event-type sets and maps that enforcement reads (`CONTROL_EVENT_TYPES`, `RESERVE_CLASS`, `MAX_UNWITNESSED_EXEMPT_TYPES`, `POWER_REDUCING_TYPES`, `SESSION_SIGNED_EVENT_TYPES`, `PR_TYPES`, `EVENT_TYPE_CODES` and the others) are now read-only views: `has`, `get`, `size`, `forEach` and iteration work as before, and there is no `add`, `delete`, `set` or `clear`. This is breaking only for code that mutated them. `EVENT_TYPES` is frozen, and the gateway's `RESERVED_TOOL_NAMES` is a read-only view in the same way.

The public store entry points read their options once, as a plain record, and always open legacy and format-1 files read only; replay `hooks` there need `inspect: true`.

`@ramex-labs/irontrellis/adapter` now hands out the same format-2 store writers as `@ramex-labs/irontrellis/store`; before, its `openHistoryStore` and `createHistoryStore` could write an older format. `resetStoreCountersForTests` and `setStoreCutHookForTests` stay public: they are test hooks, not part of the stable API, and are to be moved off public subpaths after 1.0.0-rc.2.

### Migration

- `irontrellis migrate <source> <target>` re-records a legacy or format-1 history as format 2 under a new owner key, in steps that resume after a crash (plan, target, pin, snapshot, then a `.migrated` fence beside the source). The source is never changed; once fenced it is refused by every writer and enforcing reader. `migrate --status` reports the phase from the files.

### Fixed

- The hook now limits the drain of waiting refusals to the call's `recordBudgetMs`, which the call's own refusal shares, so the verdict is no longer held behind a long spool: it waits about one budget, plus one read and one rewrite of the spool and a write in progress (not a hard real-time bound). Entries not reached stay in the spool for a later drain. The hook also reads the recorded refusals once per drain instead of opening the history for each waiting entry. The gateway's refusal path does not have these changes yet (KNOWN-ISSUES 70); it never forwards a denied call.

### Not established

- The Python package is still format 1: it refuses a format-2 history (`UNSUPPORTED_VERSION`) and its receipt verifier does not read format-2 statements. The port is pending.
- Witnesses do not hold state roots; a rollback is detected against the head, not the root.
- Budgets are only as strong as rollback detection: bind a witness with `requireOnOpen` to any history whose budgets matter. Hook checks and per-call gateway checks are never charged to a budget.
- CONNECTOR refusals and effects say what the named connector reported; replay does not prove them.
- No proof system is part of this release; the projection is the place a later prover would read.
- The coding-agent hook doesn't record a call its protective rules refuse: those rules decide before the history is opened. The session-signed records of the hook and the MCP gateway stay unattested and unwitnessed until the next owner write. The hook signs each new session with the single owner key beside the history, so it can't yet be used with a multi-signature owner policy or an offline owner key (docs/SECURITY.md §2, §3 and §6). Under Codex and Cursor the host still finds `irontrellis-hook` through PATH, so a program placed earlier on PATH can stand in for it, and a Codex PreToolUse hook that times out or crashes lets the call through ([known issue 77](docs/records/KNOWN-ISSUES-r2.5.md)).
- Chain anchors: 1.0.0-rc.2 doesn't verify them itself. Its anchor check (`verifyAnchor` in the anchor outbox) produces no report, and the MCP gateway's pre-dispatch barrier takes the mode of a report supplied from outside on its producer's word. The separate tools used for the demonstration anchoring records report `TRUSTED_NODE` only, never consensus-verified ([known issues 54 and 71](docs/records/KNOWN-ISSUES-r2.5.md)).

## 1.0.0-rc.1 - 2026-09-30

The first release of IronTrellis (formerly Continuity). It consolidates Continuity Core 0.2.x and the Core 0.3 preview API (`@ramex-labs/continuity@0.3.0-preview.8`) into one engine behind the existing API, and adds what the September 2026 evaluation found missing for real use: revocation that can never be refused, a history whose edits and rollbacks are detected, owner keys that can be rotated and kept off the agent's host, a remote witness outside the host's trust domain, and front doors for operators and coding agents. Every decision means what it meant in Continuity: 53,984 differential authorization comparisons and 773 query envelopes agree with the frozen Continuity Core 0.2.2 engine, the Continuity conformance vectors pass unchanged, and both engines write byte-identical legacy files. The deliberate departures are listed in docs/MIGRATION.md.

### Core engine and history format

- `@ramex-labs/irontrellis`: the engine (the Core 0.2 functions without the `Portable` prefix), the store and signing layer, anchoring, the remote witness client, and the local owner, runtime, execution, evidence and attempts API. Zero runtime dependencies: keccak-256 and secp256k1 recovery are vendored, Ed25519 comes from `node:crypto`. Entry points: the root, `./local`, `./store`, `./attempts`, `./transparency`, `./custody` and `./platform` (docs/API.md).
- History format `irontrellis-event/1` (docs/HISTORY-FORMAT.md): plain JSON lines with canonically sorted keys, SHA-256 record and prefix hashes, a genesis that declares the owner keys (`ownerKeys`) and, by default, the commitment to the next owner key (`nextKeyDigests`), every control event signed by an owner key in force over the previous head and the event's effect (`controlAuthorization`; replay rejects `CONTROL_AUTHORIZATION_INVALID`), per-history `maxEvents`, and a 1 GiB file limit. Format-1 event types beyond the 25 Continuity types: `ANCHOR_RECORDED`, `OWNER_KEYS_ROTATED`, `WITNESSES_BOUND`, `WITNESSES_UNBOUND`. Addresses the evaluation's third blocker: "everything after [the last signed event], revocations included, can be deleted and the hash chain recomputed."
- Pinned head (`<history>.head`) with an owner attestation after every append; every opener refuses (`ROLLBACK_DETECTED`) a file that does not contain its pin, a malformed pin, a format-1 history with events after genesis and no pin or a pin without a valid owner attestation of a prefix of the file, or a file the local anchor log shows was cut back. `acceptRollback` re-pins deliberately (recording `rollbackAcceptedAt` and the previous pin), `allowUnpinned` reads such a history for inspection, `repin()` brings the owner's attestation up to the head (refused with `REPIN_REFUSED` when the pin or an anchor log shows a rollback), `observe({ expectHead })` pins an observation. Legacy histories get a pin from their first append. Addresses "truncating the file, or restoring a backup from before a revocation, also goes undetected" and "a caller cannot pin the history head it expects."
- Anchoring: `attestHead`, `anchorHead` and `ANCHOR_RECORDED` (`data.anchor`: `local-head-file`, `rekor-v2` or `custom`). Anchor targets `localAnchorLog` (`<history>.anchors`, the offline fallback every opener and `verify` read) and `rekorAnchor` (Sigstore Rekor v2, experimental: never exercised against a live log). An anchor never binds or unbinds a remote witness.
- `verify()` / `verifyHistory` check the chain, every control signature, the pinned head and its owner attestation, every recorded anchor, every anchor log they are given (`<history>.anchors` always) and, with `verifyWithWitnesses` / `verifyHistoryWithWitnesses`, the remote witnesses; the report has `ok`, `failures` and `notes` (`CODE: explanation`). Anchor-log findings are `ANCHOR_LOG_*`, remote-witness findings `REMOTE_WITNESS_*` (docs/API.md §7). `verify()` replays once and reuses the store's cached replay when the bytes match it.
- Pluggable signature suites (`SignatureSuite`): `ed25519` (format-1 default) and `eip191-personal-sign-keccak256` (legacy, still accepted); the genesis declares the scheme, and each runtime session its own.
- Capacity policy `irontrellis-capacity/1` with modes `OPEN` and `CONTROL_ONLY`: when the budget is reached, new grants, agents, roles, sessions and jobs are refused with `CAPACITY_CONTROL_ONLY`, while revocations, terminations, unappointments, epoch advances, obligation status changes, receipts for admitted intents, anchors, owner key rotations and witness bindings are always admitted. Format-1 histories are unlimited by default. Addresses the second blocker: "after 85 grants, `revoke()` fails with `CAPACITY_RESERVED` and the grant keeps answering ALLOW."
- Owner API parity with the engine: `grant` takes `delegable`, `requires`, `independent`, `parent` and `from`; `delegate`, `prohibit` (ROOT and GLOBAL, also issued by agents), `terminate`, `unappoint`, `handover` (the offboarding report), `verify` and `capacity`. Addresses "attenuation, prohibitions and multi-party approval, the engine's most distinctive features, cannot be reached without writing raw events."
- Evaluation time defaults to the host clock on owner handles (`observe({ at })` overrides; `observeHistory` keeps the head-time default). Addresses the sixth blocker: "if nothing has been written since a grant expired, `observe()` still reads it as ALLOW."
- RESPONSIBLE answers for grants whose actions or resources were supplied unsorted, where Continuity threw `TypeError: Inconsistent internal responsibility projection inputs` (evaluation bug 1); it compares normalized grants, existing histories included.
- Input is validated once at the boundary (`captureValue`, `captureData`: accessors, proxies, symbol keys, cycles and sparse arrays are refused before any user code runs) and treated as immutable by convention; state is kept per store and applied incrementally, so a write never replays the history. State entry points (`proposeIntentAdmissionState`, `createReceiptState`, `prepareAdministrativeEventState`, `DurableAdmissionCoordinator#prepareState`, …), `forkReplayState` and `withProspectiveEvent` let the execution path, the duty writes and the gateway's jobs work on the cached state.
- Format-1 decision evidence is narrowed to the request (the genesis, the head, the actor's lifecycle, the candidate paths' authorities and intersection partners, the prohibitions considered), and format-1 receipts have no history-length bound; legacy histories keep the reference's evidence and bounds byte for byte.
- Handover (`succeed`) is validated as a whole on a copy-on-write fork before its first durable step, and stays resumable. Roles are exclusive (`createRole({ exclusive: false })` is refused up front with `INVALID_INPUT`).
- Session-signed duty writes translate producer errors (`TRANSITION_REJECTED`, `SIGNER_FAILED`, `INVALID_INPUT`, `HISTORY_CONFLICT`, each with `detail.producerError`); `IronTrellisError` carries an optional `detail`.
- Stale writer-lock recovery (`{ pid, hostname, createdAt }`; a lock older than 60 s from a dead process on the same host is reclaimed, race-free), `lockTimeoutMs`, and `STORE_BUSY` / `HISTORY_CONFLICT` naming the lock and its holder.
- Migration from Continuity: `migrateHistory` / `irontrellis migrate` re-record a `continuity-event/0.2` history verbatim as a signed format-1 history whose genesis carries `migratedFrom` and, by default, a next-key commitment; legacy runtime signatures keep verifying through the migration shadow. See Compatibility.

### Owner keys: rotation, pre-rotation, custody

- Owner key rotation (`OWNER_KEYS_ROTATED`): owner key epochs (`state.ownerKeyEpochs`), every control signature and head attestation judged by the keys in force at its position; key-set rules (a retired key id never returns, a key id is never re-bound, no key gets a second name). `LocalOwner#rotateOwnerKey`, `prepareOwnerKeyRotation` / `commitOwnerKeyRotation`, crash-safe key-file staging (`<history>.owner-key.pending.json`, archives `<history>.owner-key.<keyId>.retired.json`), `verifyRotationEvent` for a party that holds the prior epochs but not the history (a witness).
- Pre-rotation (docs/SECURITY.md §2.1): an epoch's commitment to the digests of its next keys (`ownerKeyDigest`) is fixed by the event that opens it, the genesis for the first epoch. A rotation out of a committed epoch must reveal committed keys, prove possession with signatures over its own challenge (`nextKeyAuthorizations`) and commit again, so a leaked current key alone can neither rotate nor replace the commitment. Out of an uncommitted epoch the key in force rotates freely; a rotation that keeps every key and only adds a commitment (the commitment-only rotation, `commitNextKey` / `owner commit-next-key`) is how a history without one gets one. `createLocalOwner`, `irontrellis init`, `irontrellis-hook init` and `migrate` commit in the genesis by default (`<history>.owner-next-key.json`, to be moved off the host; `nextKey: false` / `--no-next-key` opts out). `ownerKeyStatus()` / `owner status` report the commitment, its source (genesis, rotation, commitment-only rotation), `keyRotations` and `commitmentRotations`, and warn while the next key is on the host.
- Owner-key custody (docs/CUSTODY.md): an owner key file, next-key file or retired archive may hold a key reference instead of key material (`irontrellis-owner-key-ref/1`, `irontrellis-owner-next-key-ref/1`, docs/HISTORY-FORMAT.md §13.1), naming a signer that holds the key: an ssh-agent (OpenSSH, 1Password, gpg-agent with a YubiKey; the Windows named pipe), HashiCorp Vault Transit (the key version pinned, the token never in the reference; tested against a real Vault server), or any program through the command signer (Google Cloud KMS and AWS KMS examples). Every signature a signer returns is verified against the pinned public key before use. A next key can be committed by its public key alone (`--next-public-key`). Backends are extensible (`registerSignerBackend`). CLI `signer test|ref|list|to-ssh`; `owner status` reports each key's custody.
- `irontrellis doctor [--as-agent]`: a read-only audit of custody and the deployment (who holds each key, whether the current OS user can read key material or reach a signer, hooks and their protect list, witnesses, pre-rotation, history size, platform); run as the agent's OS user it fails when that user can use the owner key.
- Asynchronous signers (KMS, ssh-agent, command, Vault) work everywhere: every owner write waits for its pin attestation; a failure after the write is reported as such (CLI `WRITTEN_UNATTESTED`, exit 4: the event is recorded, `repin` later).

### Remote witness

- `@ramex-labs/irontrellis-witness` (command `irontrellis-witness`, docs/WITNESS.md): a self-hostable server, run in another trust domain, that keeps an append-only RFC 6962 Merkle log of owner-signed head statements and accepts a statement only if it extends the latest head it holds for that history. Protocol `irontrellis-witness/1`: registration of the genesis, head statements, owner key rotations through `POST /v1/histories/:id/key-events` (and an offline admin import of key-event bundles), receipts with inclusion proofs, C2SP signed-note checkpoints, consistency proofs, and a latest note (`irontrellis-witness-latest/1`) signed over the client's nonce, so a replayed older answer is refused. Conflicting statements are recorded as capped `EQUIVOCATION` evidence; a pre-rotated rotation supersedes heads a retired key pushed after the last good head (`SUPERSEDED`). Commands `init`, `serve`, `token create`, `verifier-key`, `check-log` (offline audit), `import-key-events`; rate limits, metrics, durable appends, and deployment examples (systemd, Docker with a smoke test and a GHCR workflow, Caddy, nginx).
- The client is part of the core and used by the CLI, the hooks and the gateway without configuration: a `WitnessPolicy` (`quorum`, `mode` sync or async, `maxUnwitnessedEvents`, `requireOnOpen`, `cacheMs`), the side file `<history>.witness.json`, and an out-of-band minimum policy (`IRONTRELLIS_WITNESS_POLICY`) that nothing on the agent host can lower. Owner-keyed writers check the witnesses before their first write and refuse a copy that lacks a witness's latest head (`ROLLBACK_DETECTED`, `WITNESS_AHEAD` / `WITNESS_FORK`), signing nothing for it; statements are signed under the writer lock from the state appended (`FILE_CHANGED_UNDER_WRITER` otherwise). Checkpoints are checked for consistency (`WITNESS_SPLIT_VIEW`), receipts and latest notes verified (`WITNESS_INVALID_RESPONSE`).
- Witness bindings are owner-signed control events, `WITNESSES_BOUND` and `WITNESSES_UNBOUND` (docs/HISTORY-FORMAT.md §10.1), with closed schemas checked by replay in both engines: each bound witness's URL, verifier key and signed `REGISTERED` receipt, and the owner-signed policy minimum. Bound witnesses are pinned (the side file cannot move or drop them), every check needs answers from the bound witnesses themselves, and a witness that denies a registration it signed fails verification. `createLocalOwner({ witness })` / `irontrellis init --witness` register the genesis before the file exists and write the binding with the first events. `addWitness` / `removeWitness` (with an owner-signed accepted loss for a real loss), `checkWitnesses`, `witnessStatus`, `flush`.
- Owner key rotation with bound witnesses is two-phase: every bound witness records the rotation before it is appended locally (a sealed prepared-rotation record, `<history>.rotation.pending.json`, recovers an interrupted one); `--emergency` records locally first. Rotations are delivered through the queue or key-event bundles (`owner export-key-events`), and the client supersedes automatically for a pre-rotated rotation.
- Shared wire formats on `@ramex-labs/irontrellis/transparency` and in Python: Merkle proofs, signed notes and checkpoints, head statements, log entries (`REGISTERED`, `HEAD`, `ROTATED`, `EQUIVOCATION`, `SUPERSEDED`), receipts (`verifyWitnessReceipt`), latest notes, key-event bundles.

### CLI

- `irontrellis` (unscoped package): commands from `init` to `handover`, grouped as history, owner keys, key custody, remote witnesses, structure, authority and questions; `--json` everywhere; exit codes 0/2/3 for ALLOW/DENY/INDETERMINATE, 1 for a failure, 4 for a write whose pin attestation failed afterwards. `npx irontrellis demo` is the zero-install first look. Addresses "keep zero-install as the front door" and the operator's "how do I run this for my team?"
- Plain-language messages for every error code, naming the argument and the limit for input errors and the next step for rollback, anchor-log and witness findings. Writes retry `HISTORY_CONFLICT` with backoff.

### Hooks

- `@ramex-labs/irontrellis-hooks`: `irontrellis-hook` for Claude Code, Codex CLI and Cursor. Sessions are admitted as runtime sessions, side-effecting tool calls are authorized at the host clock, handover records are written at session end, and the session opens with its open duties and permissions. Addresses "ship hooks for Claude Code, Codex and Cursor."
- The hook's state (history, owner key, session keys, handover records) lives outside the project (`~/.irontrellis/projects/<hash>/`). Protective rules refuse routed tool calls that name that state, key references, signer sockets and programs, the witness policy, or run an IronTrellis control command; they are a tripwire, documented as such, and `init --allow run-shell` needs `--i-understand-same-user-risk` (docs/SECURITY.md §2). ### MCP gateway and evidence server

### Python verifier

### Performance

- Measured, not claimed (docs/PERFORMANCE.md, docs/BENCHMARKS.md): opening a format-1 history costs about 0.13 ms per event on a 2-vCPU machine, linear to the 1 GiB limit (123 s at 1,000,000 events); after that nothing grows with the history: an append 0.55 ms (1.4 ms with fsync), a warm `authorize` 30–75 µs, a simulated job 12–35 ms at 2,000–5,000 events. Addresses the fourth blocker: "a grant took 43 milliseconds at 4 events and 1.3 seconds at 83."
- Ed25519 verifications run on worker threads during the replay of large files, speculatively (`IRONTRELLIS_VERIFY_THREADS`); `verify()` on an open handle checks a running SHA-256 instead of re-parsing; decisions for actors with many grants, SURVIVES and the Python replay are linear in the history. `bench/` generates genuine histories up to the file limit and measures them; `pnpm bench` is a CI regression check against budgets.

### Security posture

- Control events are signed and heads are pinned and attested, so a party who can only write the history directory cannot forge a grant, edit a signed event, or drop a revocation without every opener refusing the file. A rollback to a head the owner once attested is detected by a remote witness bound to the history (owner writes refuse, `verify` fails, `requireOnOpen` readers refuse); without one, only an anchor log out of the writers' reach detects it. Pre-rotation and off-host custody limit what a stolen owner key can do; a key held in force can still sign until it is rotated. docs/SECURITY.md states what is and is not established, the residual risks and the known limitations; docs/WITNESS.md §3 the remote witness's residuals.
- Internal reviews made before this release, and the fixes they led to, are recorded in docs/reviews/.

### Compatibility

Relative to Continuity Core 0.2.x and the Core 0.3 preview API:

- **Names.** Continuity is IronTrellis: `@ramex-labs/continuity` → `@ramex-labs/irontrellis`, `@ramex-labs/continuity-mcp-gateway` → `@ramex-labs/irontrellis-mcp-gateway`, `@ramex-labs/continuity-mcp` → `@ramex-labs/irontrellis-mcp`, `continuity-*` commands → `irontrellis-*`, MCP Registry `continuity-gateway` / `continuity-evidence` → `irontrellis-gateway` / `irontrellis-evidence`. The evaluation found the old name "taken in almost every direction that matters." Full table in docs/MIGRATION.md.
- **Legacy histories.** `continuity-event/0.2` files open, replay and append in place, with lines byte-identical to what the Continuity SDK writes, and every decision on them is unchanged; they gain a pinned head from their first IronTrellis append. They cannot carry the format-1 event types (owner key rotation, witness bindings, anchors: `UNSUPPORTED_EVENT_TYPE`), and a remote witness refuses them (`UNSUPPORTED_FORMAT`).
- **Migration.** `irontrellis migrate <legacy> <target>` re-records a legacy history as format 1 under a new owner key (or a key a signer holds), with the genesis committed to a next key by default; the source stays as the archive and decisions are identical. Continuity never pinned its files, so a Continuity-written source needs `--accept-unpinned-source` after it has been checked against a copy you trust. Intents admitted before the migration are answered by the source archive (`MIGRATED_INTENT`).
- **API.** Every history-appending method returns a promise (queries and `openLocalOwner` stay synchronous). The Core 0.3 subpaths `./simulation`, `./runtime`, `./evidence`, `./policy` and `./adapter` fold into `./local` and the root. Capacity never refuses a control event: the 8-slot reservation, `CAPACITY_RESERVED` and the `HISTORY_LIMIT` caps (96 managed, 128/252/256 in the attempts and execution paths) are gone, and legacy histories keep the `continuity-managed-capacity/1` name and 96-event budget but admit control events regardless. The deliberate behavioral departures from the reference are listed in docs/MIGRATION.md.
- **Deprecated.** `ContinuityError` and `ContinuityErrorCode` (aliases of `IronTrellisError` and `IronTrellisErrorCode`, removed in the release after 1.0); `POLICY` in favor of `POLICY_VERSIONS[format]`; the npm packages `@ramex-labs/continuity`, `@ramex-labs/continuity-mcp`, `@ramex-labs/continuity-mcp-gateway` and `@ramex-labs/continuity-remote` are deprecated on the registry with a pointer here.
- **Removed.** `@ramex-labs/continuity-remote` (LangChain tools and the cooperating-service contract) and, in the gateway, the cooperative-service profile, the MCP Tasks profile and the loopback HTTP transport; the tutorial, `tools/*.mjs`, `bin/continuity.mjs`, recorded runs, the website and playground build, and every committed build output (the evaluation found 49% of tracked files were generated copies); viem and the noble libraries as dependencies; `HISTORY_LIMIT` as a raised error (the code stays in the union so existing `catch` clauses compile).
