## Engine

1. **The snapshot base is written and read as one string, and Node caps a string at about 512 MiB (A-44.2).** The base snapshot is built as one JSON string to write it, and read back as one string after the `snapshot.maxBytes` check. Node 24 caps a string at 536,870,888 characters, about 512 MiB, so past that size the base can be neither written nor read. A write fails, the store catches the failure silently and tries again at the next append, so every append re-serializes the whole state. A read falls back to `SNAPSHOT_STALE` and a full replay at open. The records stay correct; only speed suffers. The 2 GiB `snapshot.maxBytes` default cannot be reached. Measured on the Linux test VM (arm64, Node 24.19.0) with a format-2 history of 64 KiB grants: about 0.7 s per append with the history at 870 to 901 MiB. Status: open; rc.3 streams the base and stops the retries.
2. **The string limit does not stop the history itself at the cap (measured).** A format-2 file is read into one buffer, not one string; line parsing builds one string per line. Measured on the Linux test VM (arm64, Node 24.19.0): a 1,004 MiB history of 16,066 events (64 KiB grants), just below the reserve threshold, opened in 32.9 s with its snapshot files present (they had stopped updating, entry 1) and in 31.0 s replaying in full, verified in 32.1 s and took a control write; peak memory over the run was 6.1 GiB. Writing it took 87 minutes, slowed by entry 1. Status: works at the cap; the time and memory go to rc.3's performance work with entries 1 and 32.
3. **Export view and B(from) (§15, A-65).** The view carries no byte measure at `from`; a verifier starting at `from > 0` cannot judge the A-3 byte limits for the range (it notes it). Ranges from 0 are exact. Why: SPEC §15 has no field for it; A-75.3 makes `B(from)` later work (E-16).
4. **Export closure is a superset (A-65.3).** The exporter carries every body the rebuild reads, including all type-40 and type-35 bodies before `from` (the A-36.1 envelope index and the A-46.3 checkpoint-id set are rebuilt from them), not only the cited ones. Disclosed by construction; it can make views larger than necessary.
5. **Frozen generator and A-50.** `conformance/v2/generate/lib.mjs` (frozen) computes `carryIn` without the A-50 saturation; the budget differential in `format2-budgets.test.mjs` skips the requests where it diverges (5 of 2000, printed). The A-50 vectors are in `conformance/v2-regenerated`.
6. **Append budget (A-4.3).** Every format-2 append computes the exact §7.1 root. The engine keeps the cache of unchanged subtrees that A-67 allows, but an insertion still rehashes every subtree to its right (docs/BENCHMARKS.md). Why: A-4; an O(log n) append needs a format change.
7. **Prover cache.** Format-2 authority proofs are recomputed per decision; the prover keeps no cross-call cache (G1 note 8).
8. **An EIP-191 session in an Ed25519 deployment** is accepted as in the 1.0.0-rc.1 engine (the session scheme is per session); A-32.2's subgroup test applies to Ed25519 keys only.
9. **Strict Ed25519 pre-checks in format 1.** The A-32.1 pre-checks live in the shared verifier, so a format-1 history with a non-canonical or small-order signature component is now refused where the 1.0.0-rc.1 engine accepted it (no v1 or legacy vector is affected; a real-world format-1 file signed by the engine never carries such a signature).
10. **A-46.2 RESERVE suppression is not exercised end to end** (it needs about a million records); covered by code reading only.
11. **`USAGE_CHARGED` is future work (A-25.3, founder).** Hooks do not charge count budgets; budgets bind admitted intents only. Since S5-38 the CHANGELOG lists it as future work (proposed 49, closed). Status: open, a founder decision.

## Hooks and the gateway

12. **Spool drains (A-38.2).** Only a process holding the actor's session drains; the CONNECTOR-shape drain by another process (an owner write, another agent's hook) is not built, so entries of an actor whose session is gone wait in the spool. A CONNECTOR refusal (A-42) that misses its budget is reported `RECORD_DEADLINE` and not spooled.
13. **A process that exits right after `SPOOLED`** abandons the slow write; the next drain records the entry (or finds it recorded: the refusal id is fixed before the race).
14. **The evidence tool uses its `operationId` as a raw intent id** (A-37.2 allows it; the caller owns the collision risk). Another admitted session could take that id first.

## Migration

15. **A-63:** format-1 histories with a key rotation or a witness binding cannot be migrated in this format (`SOURCE_KEY_ROTATED` / `SOURCE_WITNESS_BOUND`); they stay readable and verifiable read only. Lifting this needs a later format-2 addendum (A-63.3).

Without a remote witness the tool never calls `flush()`; with one, it calls it and drops every error except `ROLLBACK_DETECTED` and `WITNESS_SPLIT_VIEW`. So with an asynchronous owner signer (an owner key reference to ssh-agent, a command or a KMS) that signs the revocation and then fails the pin attestation (a declined touch, a timeout), the operator is told the revocation succeeded, with no hint to run `repin`. The revocation then sits in the unattested tail, where a copy cut back to the last attested head still verifies (SECURITY.md §3), so someone who can write the history directory could remove it unnoticed unless a witness or an anchor log holds a later head. The `irontrellis` command reports the same case as `WRITTEN_UNATTESTED` (exit 4); use `irontrellis authority revoke` when the owner key is held by an asynchronous signer. Confirmed by reading the code; not reproduced. Status: open; the fix (report the attestation failure, as the CLI does) comes after launch.
