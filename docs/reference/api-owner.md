`createLocalOwner` writes the genesis (for format 1 with its next-key commitment, unless `nextKey: false`) and `PRINCIPAL_CREATED` (position 0 and 1), then `WITNESSES_BOUND` when `witness` names witnesses (position 2), all in one write, and fails with `HISTORY_EXISTS` if the file exists. Without a `signer`, a format-1 history gets a fresh key file; a key file already at `<historyFile>.owner-key.json` is refused (`KEY_EXISTS`, `detail.keyPath`) unless `reuseExistingKey`, and so is a next-key file already at `<historyFile>.owner-next-key.json`; key files created for a history that could not be written are removed again. `createLocalAttemptOwner` and `createLocalReviewOwner` do the same with the E5 and E6 adapter policies (needed for the attempt recorder). `openLocalOwner` opens an existing file of either format, refusing a pin, anchor-log or witness problem with `ROLLBACK_DETECTED`, `ANCHOR_LOG_UNREADABLE` or `WITNESS_UNREADABLE` (§11) unless `acceptRollback` or, for reading, `allowUnpinned`. With an asynchronous (KMS) `signer`, `createLocalOwner` waits for the attestation of the first pin before it returns. A missing or unusable owner key file (including one that group or others can read) leaves the handle read-only for control events (`KEY_UNAVAILABLE` on the first write), never fails the open. `createLocalDomain({ format? })` returns a fresh domain with `deploymentId: "local:<uuid>"` (legacy domains get placeholder chain fields).

#### `rotateOwnerKey(input?)`

Replaces the owner key set (`docs/HISTORY-FORMAT.md` §7.1–7.2). What the new key must be depends on the owner keys in force:

* **They committed to a next key** (pre-rotation; the default for a history `createLocalOwner` made): the new owner key is the committed key, from `nextKeyFile` (default `<history>.owner-next-key.json` when it is there) or `nextSigner`. Without it the call refuses with `KEY_UNAVAILABLE` (`detail.nextKeyDigests`, `detail.nextKeyFile`) and writes nothing; a file or signer holding another key is `KEY_UNAVAILABLE` too (`detail.digest`). The event carries the key's proof of possession (`nextKeyAuthorizations`, signed over the event's own control-authorization challenge) and commits the new set to a fresh next key (`nextKeyDigests`). `newSigner` and `nextKey: false` are refused (`INVALID_INPUT`).
* **They have no commitment**: a new Ed25519 key file (or `newSigner`) becomes the owner key, and a fresh next key is committed unless `nextKey: false`.

Input (`OwnerKeyRotation`, every field optional):

| field | meaning |
|---|---|
| `nextKeyFile` | path of the next-key file holding the committed key (pre-rotation). It becomes `<history>.owner-key.json`; a file outside the history's directory is left as it is (it now holds the owner key in force) |
| `nextSigner` | the committed key as a `Signer` (offline HSM, KMS); it becomes the handle's owner signer |
| `newNextSigner` | the key the new set commits to next, as a `Signer`. Default: a fresh Ed25519 next-key file, staged as `<history>.owner-next-key.pending.json` and moved to `<history>.owner-next-key.json` |
| `nextKey` | `false`: record no commitment for the new set (only when the keys in force have none) |
| `newSigner` | without a commitment: the new owner key as a `Signer` (e.g. a KMS key). Without it a new Ed25519 key file is generated and replaces `<history>.owner-key.json` |
| `keyId` | id of the new owner key; default the id the next-key file proposes (when free), else the next free `owner:N`. With `newSigner` / `nextSigner` it must equal that signer's `keyId`. A key id this history ever used is refused (`INVALID_INPUT`) |
| `reason` | recorded in the event; 1..256 UTF-8 bytes, no control characters |
| `emergency` | `true`: record the rotation locally first and deliver it to the witnesses afterwards (`docs/WITNESS.md` §7.2). Without it, a history that binds remote witnesses rotates in two phases (below) |
| `retire` | `"all"` (default: the new set is the new key alone) or a list of current key ids to drop (`[]` adds a key and retires nothing). A key file (generated or promoted) cannot replace a key file whose key stays in force (`INVALID_INPUT`: retire it too, or pass `newSigner` / `nextSigner`) |

Result (`OwnerKeyRotationResult`): `{ eventId, head, keyId, ownerKeys, retired, fromPosition, keyFile?, retiredKeyFile?, preRotated, nextKeyDigests?, nextKeyFile?, nextKeyId?, commitmentOnly?, witnesses?, rotationIncomplete?, emergency?, bundle? }`. `head` is the head that ends with the rotation (position `r`, pinned and attested under the old key set); `fromPosition` = `r + 1`, from which `ownerKeys` sign. `preRotated` says the rotation satisfied a commitment; `nextKeyDigests` is the new set's commitment and `nextKeyFile` where its generated key is. After the call the handle, and its store's pin attestations, use the new key. With remote witnesses: `witnesses` is `{ accepted: [url], refused: [{ url, code, message }], unknown: [{ url, message }] }` for the two-phase delivery, `rotationIncomplete` is `true` while a bound witness has not recorded the rotation (it is queued for it), `emergency` echoes the input, and `bundle` is the path of the rotation's key-event bundle.

**Two-phase rotation with bound witnesses** (`docs/WITNESS.md` §7.1). When the history binds remote witnesses and `emergency` is not set, `rotateOwnerKey` first flushes and requires every bound witness to have answered with exactly the local head (`WITNESS_UNAVAILABLE`, `detail.reason: "ROTATION_NEEDS_WITNESSES"`, `detail.witnesses`, nothing prepared). Then, under the writer lock, it prepares the rotation (as `prepareOwnerKeyRotation`), signs the old-key statement for its head, writes the sealed prepared-rotation record `<history>.rotation.pending.json` (`docs/HISTORY-FORMAT.md` §13) and delivers the rotation with that statement to every bound witness (`POST …/key-events`). If at least one accepted, it appends exactly the prepared event and swaps the key files; the witnesses that did not accept get it from the queue (`rotationIncomplete: true`). If none accepted: every refusal definite → `WITNESS_UNAVAILABLE`, `detail.reason: "ROTATION_ABORTED"` (`detail.refused`), nothing appended, the staged files and the record removed, message *rotation needs every bound witness; retry, or rotate with --emergency*; some outcome unknown → `WITNESS_UNAVAILABLE`, `detail.reason: "ROTATION_OUTCOME_UNKNOWN"` (`detail.pendingPath`, `detail.unknown`), the record and staged files kept. While a record is outstanding, every write of every handle refuses with `WITNESS_UNAVAILABLE`, `detail.reason: "ROTATION_PENDING"` (`detail.position`, `detail.pendingPath`) until an owner command (any owner-keyed write, `flush()`, `rotateOwnerKey`) asks the bound witnesses: one that holds the prepared head makes the store append the prepared event (no new attestation is signed; the rotation's key files are settled), and when every bound witness answered and none holds it the record is discarded. `rotateOwnerKey({ emergency: true })` with an outstanding record records that prepared rotation (only when the handle holds its staged or given new key). A history without bound witnesses always rotates local-first.

`setRotationFaultForTests(point)` (with `RotationFault`) injects a simulated crash at `"after-stage"`, `"after-record"`, `"after-delivery"`, `"after-append"` or `"after-owner-key-swap"` for tests; `undefined` clears it.

**Prepare and commit.** A local-first `rotateOwnerKey` is `prepareOwnerKeyRotation` then `commitOwnerKeyRotation` under one writer lock. `prepareOwnerKeyRotation(input)` settles leftover key files, stages the key files the rotation needs (below), builds and signs the event (its `controlAuthorization` and `nextKeyAuthorizations`), checks it against the current state (`withProspectiveEvent`, every replay rule) and computes the head it will produce with the store's history hasher, and returns `PreparedOwnerKeyRotation` = `{ event, previousHead, head, ownerKeys, keyId, retired, fromPosition, preRotated, nextKeyDigests?, signedBy, files: { pendingKeyFile?, pendingNextKeyFile?, nextKeySource? } }` without appending anything. `commitOwnerKeyRotation(prepared)` checks that the staged files still hold the prepared keys (`KEY_UNAVAILABLE`, nothing recorded, when another process removed them), appends exactly `prepared.event` at `prepared.previousHead` (`HISTORY_CONFLICT` if the history moved; the staged files are then removed), asserts that the recorded head equals `prepared.head` (`WRITE_UNCONFIRMED` otherwise), hands the rotation to the remote witnesses (afterwards: local-first, as `emergency`; the two-phase delivery belongs to `rotateOwnerKey`) and swaps the key files. A prepared record is committed at most once, and only by the handle that prepared it (`INVALID_INPUT`). A prepared rotation that is never committed leaves only pending key files, which the next open or rotation removes.

**Key files and crash safety.** Three files are involved: the current key (`<history>.owner-key.json`, K), the next key (`<history>.owner-next-key.json`, N) and the retired archive (`<history>.owner-key.<keyId>.retired.json`, R). In order, all under the writer lock: (1) settle any earlier pending files (below); (2) stage the new owner key as `<history>.owner-key.pending.json` (Kp: a generated key, or the committed next key rewritten as an owner key file; exclusive, 0600, fsync); (3) stage the fresh next key as `<history>.owner-next-key.pending.json` (Np; temp file linked into place, 0600); (4) append `OWNER_KEYS_ROTATED`; (5) copy K to R (0600, temp + fsync + rename); (6) rename Kp over K; (7) rename Np over N; fsync the directory after each rename. Recovery (`openLocalOwner`, the next rotation, the next control write of a handle whose key was retired) settles K first, then N:

| crash after | files left | recovery |
|---|---|---|
| (2) | Kp | its key is not declared: Kp removed; K and N unchanged |
| (3) | Kp, Np | Kp removed; no epoch committed to Np's key: Np removed |
| (4) | K = old key, Kp, N = revealed key (or none), Np | Kp's key is in force: K archived to R, Kp → K; Np's digest is the current commitment: Np → N |
| (5) | R, K = old key, Kp, N, Np | as above (the archive is not written twice) |
| (6) | R, K = new key, N = revealed key, Np | Np → N (N's key is the owner key K now holds, so it may be replaced) |
| (7) | R, K, N | nothing to do |

A next-key file is replaced only when it holds a copy of a key the history declared (the key the rotation revealed, or a retired one): never while it holds the committed key itself, a key the history never declared, or something unreadable. A rotation that would stage a fresh next key refuses such a file up front (`KEY_EXISTS`: move it aside). With `newSigner` / `nextSigner`, no owner key file is staged; a key file whose key the rotation retired is archived the same way and removed. With `newNextSigner`, no next key is staged; a next-key file from which the rotation took the revealed key is removed once the owner key file holds that key. An unreadable pending file is left for the operator and blocks the next rotation (`KEY_EXISTS`). A handle opened before another handle rotated reloads `<history>.owner-key.json` on its next control write; a caller-supplied `signer` is never replaced behind the caller's back.

#### `commitNextKey(input?)` and `ownerKeyStatus()`

`commitNextKey` gives a commitment to owner keys in force that have none (a history made with `nextKey: false`, or a rotation that committed nothing): it records a **commitment-only rotation**, an `OWNER_KEYS_ROTATED` that keeps every owner key and carries `nextKeyDigests` (`docs/HISTORY-FORMAT.md` §7.2), signed by the owner key in force (`KEY_UNAVAILABLE` without it), through the same path as `rotateOwnerKey` (two-phase with bound witnesses unless `emergency`). The next key is `nextSigner`, `nextPublicKey` (a key whose private half never touches this host; nothing is written and the result's `keyId` is the next free `owner:N` it proposes), `nextKeyReference` (a key a signer holds; the reference is staged and moved to `<history>.owner-next-key.json` like a generated key, §7b), or by default a new Ed25519 key staged as `<history>.owner-next-key.pending.json` and moved to `<history>.owner-next-key.json` once recorded (a crash in between: moved on the next open when recorded, removed when not). `reason` defaults to `next-key commitment`. Refusals, with nothing written: `TRANSITION_REJECTED` when the keys in force already have a commitment (only a rotation to the committed key starts a new one), `KEY_EXISTS` when a next-key file (or a pending one) is already there, `INVALID_INPUT` for a key the history declared. Result (`NextKeyCommitmentResult`): `{ eventId, head, nextKeyDigests, keyId, nextKeyFile?, bundle?, witnesses?, rotationIncomplete?, emergency? }`; with remote witnesses the rotation is delivered like any other (`docs/WITNESS.md` §7.5) and its key-event bundle written (`bundle`).

`ownerKeyStatus()` (and `ownerKeyStatusOf(historyFile, state)` for any reader) → `OwnerKeyStatus` = `{ format, ownerKeys, fromPosition, keyRotations, commitmentRotations, commitment: { nextKeyDigests, eventId, position, source } | null, ownerKeyFile, nextKeyFile: { path, state, keyId?, digest?, holder?, signer? } | null, nextKeyOnHost, pending, warnings: [{ code, message, path? }], custody }`, reading files only. `keyRotations` counts the rotations that changed the owner keys, `commitmentRotations` the commitment-only ones. `commitment.source` is the event that opened the epoch in force with its commitment: `GENESIS`, `ROTATION` or `COMMITMENT` (a commitment-only rotation). `nextKeyFile.state` is `COMMITTED`, `IN_FORCE` (a stale copy of an owner key in force), `RETIRED`, `UNCOMMITTED` or `UNREADABLE`, and `holder` is `file` or `reference` (`signer` names the reference's backend kind). The warning codes are `NEXT_KEY_ON_HOST` (its message ends with `NEXT_KEY_ON_HOST_WARNING` = "move it offline; pre-rotation only protects you if the next key is not on this host"), `NO_NEXT_KEY_COMMITMENT`, `NEXT_KEY_STALE`, `NEXT_KEY_RETIRED`, `NEXT_KEY_UNCOMMITTED`, `NEXT_KEY_UNREADABLE`, `KEY_FILE_PENDING` and `NEXT_KEY_SAME_SIGNER` (the committed next key's reference names the same signer as the owner key's: same ssh-agent socket, same command). `custody: KeyCustody[]` has one entry per owner key in force, for the next key, and per archived retired key: `{ role: "current" | "next" | "retired", keyId?, holder: "file" | "reference" | "public-key-only" | "elsewhere" | "none" | "unreadable", signer?, description?, path?, level: "OK" | "WARN", code, message }`, with codes `OWNER_KEY_FILE_ON_HOST` (WARN: private key material in a file on this host), `OWNER_KEY_REFERENCE`, `OWNER_KEY_ELSEWHERE`, `NEXT_KEY_ON_HOST` (WARN), `NEXT_KEY_REFERENCE`, `NEXT_KEY_SAME_SIGNER` (WARN), `NEXT_KEY_OFF_HOST`, `NO_NEXT_KEY_COMMITMENT` (WARN), `RETIRED_KEY_FILE` (WARN), `RETIRED_KEY_REFERENCE`, `KEY_FILE_UNREADABLE` (WARN). No signer is contacted.

#### Owner approval policies (format 2)

A format-2 history can require several owner keys to sign a control event (`docs/HISTORY-FORMAT.md` §15). `OwnerPolicy` is `{ threshold, byType?, keyClasses?, labels?, acknowledged?, humanFloor?, attesters?, attestations?, recovery? }` (the rules are in `docs/reference/owner-policy.md`). A `LocalOwner` holds one owner key, so an event that needs more signatures is written in two steps:

1. `prepareControlEvent({ type, data })` fixes the event at the current head: its id, timestamp and `data`, without signatures. `data` is the event's format-2 data, for example `{ grant }` for `AUTHORITY_GRANTED`. It returns `PreparedControlEvent` = `{ event, previousHead, challenge, challengeHash, required, signers }`. `required` is the number of owner signatures the policy in force needs for this type. `signers` lists the owner keys in force with `{ keyId, scheme, credential, class, counts }`; `counts` is false for an `AGENT` key on an `OWNER_KEYS_ROTATED`. A rotation that changes owner keys goes through `prepareOwnerKeyRotation` instead, because it stages key files (`INVALID_INPUT`).
2. Each owner signs `challengeHash` wherever the key is kept. `authorizeControlEvent(signer, prepared, { historyId? })` does this with any `Signer` and returns `{ keyId, signature }`; the signer sees purpose `control-authorization`.
3. `submitControlEvent(prepared, authorizations)` makes the first entry `controlAuthorization` and the rest `additionalControlAuthorizations`. It refuses with `HISTORY_CONFLICT` if the history moved after `prepare`; prepare again, because a signature is never moved to a new head. It refuses with `CONTROL_AUTHORIZATION_INVALID` (`detail.required`, `detail.present`) before writing anything when the signatures do not meet the policy. Otherwise it appends the event like any owner write.

The one-step methods (`grant`, `revoke`, `checkpoint` and the rest) still work when the policy lets the handle's key sign the type alone. When it does not, they refuse with `CONTROL_AUTHORIZATION_INVALID` (`detail.required`, `detail.present`) and write nothing. An automatic checkpoint that the key cannot sign alone is skipped and reported as `CHECKPOINT_SUPPRESSED` with reason `NO_SIGNER`.

**Changing the policy.** `rotateOwnerPolicy({ ownerPolicy })` keeps every owner key and the next-key commitment and sets a new policy. `{ resetPolicy: true }` returns to the default `{threshold: 1}`. `prepareOwnerPolicyRotation` does the same in two steps. A key rotation (`rotateOwnerKey`, `prepareOwnerKeyRotation`) and `commitNextKey` accept `ownerPolicy` and `resetPolicy` too. `commitNextKey` restates the policy in force by default. A key rotation without `ownerPolicy` would return a non-default policy to the default, so it is refused with `INVALID_INPUT` and `detail.reason: "POLICY_RESET"` unless you pass `resetPolicy: true` or restate the policy. When the rotation threshold is 2 or more, prepare the key rotation with `prepareOwnerKeyRotation`, collect the other signatures over its `challengeHash` (the prepared rotation also carries `required` and `challenge`), and pass them to `commitOwnerKeyRotation(prepared, { additionalAuthorizations })`. `ownerKeyStatus()` adds `policyRotations` and `ownerPolicy` (`null` for the default). On the command line, `irontrellis owner rotate-key` and `owner commit-next-key` take `--owner-policy <file>` (a JSON policy) and `--reset-policy`, and `owner status` shows the policy in force.

**Human attestation and time.** Under `humanFloor: "ATTESTED"`, `signers` shows each key's class at the event's time (`HUMAN`, `AGENT`, `LAPSED` or `NONE`). Two writer checks refuse before anything is signed or written, with `TRANSITION_REJECTED`. A session-signed write that would pass a statement's expiry carries `detail.reason: "ATTESTATION_EXPIRY"` and `detail.expiresAt`. A control event with one human signer past the last expiry carries `detail.reason: "ATTESTATION_HORIZON"` and `detail.horizon`. The writer never throws the replay code `TRANSITION_INVALID`.

**Limits in this release.** The handover `succeed` step, witness binding, the two-phase `rotateOwnerKey` and `commitNextKey` are signed by the handle's key alone. The local writer cannot produce a recovery rotation (known issue 24): recovering a lost quorum needs an external producer of the event, which this release neither ships nor documents ([owner policies](owner-policy.md), §4). A snapshot resume uses a pin only when its signer is qualified and one key may sign a checkpoint under the policy after the file's head; otherwise it uses an in-file checkpoint or replays in full, and `verify()` notes `FULL_REPLAY` with the reason.

Lifecycle:

| method | meaning |
|---|---|
| `flush()` | `Promise<void>`: resolves once every pending head attestation has been written to `<history>.head`. With a local key file each write attests synchronously; with an asynchronous signer (a KMS/HSM `signer`, a key reference) every owner write waits for its attestation before it returns, so `flush()` only reports a failure. A failed attestation rejects once, with `SIGNER_FAILED` or `KEY_UNAVAILABLE` (the signer failed after the write: the message says the events are durable) or `WRITE_UNCONFIRMED` (the pin could not be rewritten); the recorded events are durable either way. Still call it before a short-lived process exits (the CLI and the hooks do) |
| `close()` | releases the store's cached history; every later call on the handle fails with `READ_UNAVAILABLE`. Idempotent. It does not wait for pending attestations: call `flush()` first when a KMS signer is configured |
| `checkWitnesses({ force? })` | `Promise<WitnessView>`: asks the remote witnesses now (§7a); lifts the `requireOnOpen` gate |
| `addWitness(config, update?, { allowOffline? })` | `Promise<WitnessChange>`: adds a remote witness (§7a). Before anything is written it checks that the witness serves `config.verifierKey`, registers the genesis, checks that any head the witness already holds is a prefix of the file, and that every head statement the witness still needs can be signed (a rotation head it has not recorded needs the key that rotation retired). Then it writes the policy with `update` (`{ quorum?, mode?, maxUnwitnessedEvents?, requireOnOpen?, cacheMs? }`), brings the witnesses up to the head, binds the witness in the history (an owner-signed `WITNESSES_BOUND` carrying its signed REGISTERED receipt) and submits the head. Failures write nothing: `WITNESS_REJECTED` (a refusal, another key, an invalid answer; `detail.cause`), `KEY_UNAVAILABLE` (`detail.positions`), `ROLLBACK_DETECTED`, `WITNESS_UNAVAILABLE` (unreachable; `allowOffline: true` binds it without a receipt and lets the queue register it). Returns `{ witness, bound, eventId?, status, submitted, error?, registered }` |
| `removeWitness(urlOrKey \| urlsOrKeys, { acceptRemoteLoss?, reason? })` | `Promise<WitnessChange>`: an owner-signed unbinding (`WITNESSES_UNBOUND`) of the witnesses the history binds (refused like any write while a witness shows a rollback), then the side-file policy. A witness that refused the registration or denies one does not block its own removal. `acceptRemoteLoss: true` with a `reason` (1..256 bytes) is the owner's decision to continue on this copy although the named witnesses hold heads it lacks: it needs the owner key in force (`KEY_UNAVAILABLE`) and each witness's own verified answer showing the loss (`INVALID_INPUT`, `detail.reason: "NO_LOSS"` otherwise), sets aside only those witnesses' findings (any other witness still refuses the write), and records `acceptedLoss: { reason, heads }` in the unbinding. A witness known only from the side file is removed from it; no event is written for it. A witness the out-of-band minimum policy names cannot be removed (`INVALID_INPUT`). Returns `{ …, removed, acceptedLoss? }` |

With remote witnesses, `flush()` also waits until a quorum holds the current head: queued head statements and rotations are submitted now, and it rejects with `ROLLBACK_DETECTED` / `WITNESS_SPLIT_VIEW` on witness evidence or `WITNESS_UNAVAILABLE` when the witnesses do not hold the head yet (the events stay recorded). A short-lived process in `async` mode should `await owner.flush()` before it exits; the CLI and the hooks do.

`Action` is `{ actor, action, resource, amount?: bigint, counterparty?, termsCommitment?: Hash }`.
