## 6. Operations and incident response

### 6.1 What each finding means

| finding | where | what it means | what to do |
|---|---|---|---|
| `ROLLBACK_DETECTED`, reason `WITNESS_AHEAD` | open, write, `verify` (as `REMOTE_WITNESS_ROLLBACK`) | a witness holds an owner-signed head past the end of this file: events were removed, or an older copy was restored | §6.2. Nothing was written and no statement was signed for this copy |
| `ROLLBACK_DETECTED`, reason `WITNESS_FORK` | same | a witness holds a different head at a position this file has: the file was rewritten or replaced by another copy. With `detail.equivocationIndex`: the witness answered one of this handle's statements with `EQUIVOCATION` and recorded it as evidence (the file changed underneath the process between its check and its submission) | §6.2; this handle signs nothing more. If no copy was restored or rolled back on purpose, treat the owner key as compromised and rotate it (§7) |
| `ROLLBACK_DETECTED`, reason `FILE_CHANGED_UNDER_WRITER` | owner write, `flush`, `witness sync` | the file on disk no longer contains the head this owner process appended (or verified under the writer lock): it was swapped for another copy behind the writer's back (§2.3). Sticky for that process; nothing was signed for the copy on disk | treat it as tampering on the host. Find out which copy is the real one (`irontrellis witness status` shows what the witnesses hold), restore it (§6.2), and start a new owner process |
| `detail.source: "recorded"` on either | open | the finding comes from the side file's remembered witness head, not from the network | the same: the side file can only add findings. If you are certain the side file is wrong (it came from another history), move it aside deliberately; the witnesses are asked again |
| `WITNESS_SPLIT_VIEW` / `REMOTE_WITNESS_SPLIT_VIEW` | any | a witness could not prove its current checkpoint consistent with one this client saw before: it has shown two logs. Sticky, and recorded in the side file so later handles refuse too | stop trusting that witness. Compare its `checkpoints.jsonl` with the checkpoint recorded in the side file, run `check-log`, ask its operator whether the data directory was restored from a backup (§4.6). Then `irontrellis witness remove` it, or `irontrellis witness add` it again deliberately (which clears the record) |
| `WITNESS_UNAVAILABLE`, reason `MAX_UNWITNESSED` | owner write | `maxUnwitnessedEvents` events are not held by a quorum; writes are refused, reads continue | bring the witness back (or fix the network), then `irontrellis witness sync` |
| `WITNESS_UNAVAILABLE`, reason `UNREACHABLE` / `NOT_CHECKED` | check, `requireOnOpen` read | too few witnesses answered a check | as above; recorded events stay recorded |
| `WITNESS_UNAVAILABLE`, reason `INVALID_ANSWER` (`detail.cause` `WITNESS_INVALID_RESPONSE`); `REMOTE_WITNESS_INVALID` in `verify` | check, owner write, `requireOnOpen` read | too few witnesses gave an answer that verifies, and at least one gave an answer that does not: a missing or wrong signed latest note (a replayed older answer, `NONCE_MISMATCH`, or a `latest` that is not the one the note names), a tampered receipt, a checkpoint signed by another key. Not unavailability: owner writes are refused (nothing is appended) and the `requireOnOpen` gate stays closed; every write asks again | check the network path to the witness (use `https`), the URL and the verifier key; if a relay or proxy rewrites answers, fix it |
| `WITNESS_REJECTED`, reason `REGISTRATION_REFUSED` | owner write, `witness status` (`rejected`), `init` / `createLocalOwner`, `witness add` | a witness refused to register the history (401 `UNAUTHORIZED`: no or a wrong token; 400 `INVALID_GENESIS` / `UNSUPPORTED_FORMAT`). It can never witness this history as configured, so owner-keyed writes are refused at once (not after `maxUnwitnessedEvents`), sticky until the policy for that witness changes. At creation or in `witness add` the same refusal fails the command and nothing is written | give the token: `irontrellis witness add <url> --verifier-key <key> --token <token>` (a new config clears the state), or `irontrellis witness remove <url>`. 503 `HISTORY_LIMIT_REACHED` is not a refusal: the witness is full, which its operator can fix, so it counts as unavailability |
| `WITNESS_UNAVAILABLE`, reason `REGISTRATION_DENIED` (`detail.cause` `WITNESS_INVALID_RESPONSE`); `REMOTE_WITNESS_INVALID: … denies a registration it signed` in `verify` | check, owner write, `verify` | a witness the history binds with its own signed REGISTERED receipt answers "not registered": its data directory was restored from before the registration or lost, or an attacker in the path is answering for it. The client does not register again (that would hide the loss); the `requireOnOpen` gate stays closed, owner writes refuse, `verify` fails whatever the quorum. A witness that is only configured keeps answering `REMOTE_WITNESS_UNREGISTERED` as a note; one bound without a receipt (`--allow-offline`) counts as unreachable instead (`REMOTE_WITNESS_BINDING_WITHOUT_RECEIPT`) | ask the witness's operator (§6.4) and check the network path. If the witness really lost the history, remove it (`witness remove`: a denial is not rollback evidence, so a plain removal works) and add a new one |
| `WITNESS_UNAVAILABLE` with `detail.cause` `WITNESS_REJECTED` or `WITNESS_INVALID_RESPONSE` | owner API | a witness refused a statement or rotation (the code and hint are in the detail), or gave an answer that does not verify with its key | a rejection with `SIGNATURE_INVALID` usually means the witness lacks a rotation the client could not post (§7); an invalid response means the witness at that URL is not serving the configured key's log correctly: check the URL, the key, and the proxy |
| `INVALID_INPUT`, reason `INSECURE_HTTP` | `witness add`, `init --witness`, any open whose policy names such a URL | a plain `http:` witness URL to a host that is not loopback (§4.3) | use `https:`; `--allow-insecure-http` (`allowInsecureHttp`) only where readable traffic and cheap interference are acceptable |
| `WITNESS_UNREADABLE`, reason `WITNESS_POLICY_UNREADABLE` | every open | `IRONTRELLIS_WITNESS_POLICY` names a file that cannot be used (§5.4) | fix the file or the variable |
| `KEY_UNAVAILABLE` from `witness sync` | owner | a queued statement needs a key that is no longer on disk (the rotation head's old key, §7) | restore the retired key file beside the history, then `irontrellis witness sync` |
| `REMOTE_WITNESS_UNREACHABLE` | `verify` failure | fewer than `witnesses − quorum + 1` answered: a restored older copy cannot be ruled out | bring the witness back and verify again; `--allow-unreachable-witness` turns it into a note when you accept that |
| `REMOTE_WITNESS_INVALID` | `verify` failure | an answer that does not verify with the configured key (receipt, checkpoint, latest note or proof); `--allow-unreachable-witness` does not accept it | as for `INVALID_ANSWER` above |
| `UNWITNESSED_TAIL n` | `verify` note | the last `n` events are not held by a quorum yet | normal in async mode between writes; `irontrellis witness sync` |
| `REMOTE_WITNESS_BINDING_WITHOUT_RECEIPT` | `verify` note, `witness status` (`bindingWithoutReceipt`) | the history binds a witness without its signed REGISTERED receipt (it was bound with `--allow-offline`). Its unsigned "not registered" answers count as unreachable for readers and `verify` (reason `UNSIGNED_NOT_REGISTERED`), and it gets no sealed-cache shortcut | `irontrellis witness add <url> --verifier-key <key>` again while the witness is reachable: a new binding records the receipt |
| `REMOTE_WITNESS_UNREGISTERED` | `verify` note | a witness the history does not bind (it is only configured) does not know the history: nothing was submitted to it yet | the next owner write, or `witness sync`, registers it |
| `REMOTE_WITNESS_NOT_CONSULTED` | note | a synchronous `verify()` (or `--no-remote`, or the Python verifier) did not ask the witnesses | run `irontrellis verify` |
| `REMOTE_WITNESS_EQUIVOCATION_RECORDED n` | `verify` note, `witness status`; a WARNING in the CLI output | the witness recorded `n` owner-signed statements that conflict with heads it holds for this history | §6.3 |
| `WITNESS_UNAVAILABLE`, reason `ROTATION_NEEDS_WITNESSES` | `owner rotate-key` | after the flush a bound witness did not answer, or its latest is not the local head (`detail.witnesses`): the two-phase rotation needs every bound witness at the head (§7.1). Nothing was prepared | bring the witness back and retry; if the key must be replaced now, `irontrellis owner rotate-key --emergency` (§7.2) |
| `WITNESS_UNAVAILABLE`, reason `ROTATION_ABORTED` | `owner rotate-key` | no bound witness accepted the prepared rotation and each refused definitely (`detail.refused`). Nothing was appended; the staged key files and the prepared record were removed | fix what the refusal names (usually a witness that is not at the head), retry, or rotate with `--emergency` |
| `WITNESS_UNAVAILABLE`, reason `ROTATION_OUTCOME_UNKNOWN` | `owner rotate-key` | no witness is known to have accepted, but for some the answer was lost (`detail.unknown`). The prepared record and the staged key files are kept (`detail.pendingPath`) | run any owner command (`irontrellis witness sync`) once the witness answers: it appends the rotation if a witness holds it, discards it otherwise (§7.1) |
| `WITNESS_UNAVAILABLE`, reason `ROTATION_PENDING` | owner write, `owner rotate-key` | a prepared rotation is outstanding (an interrupted or undecided two-phase rotation, §7.1): writes wait until an owner command learns from every bound witness whether it holds the rotation's head | `irontrellis witness sync` while the witnesses are reachable; `owner rotate-key --emergency` records the prepared rotation now (only with its staged key) |
| `REMOTE_WITNESS_ROTATION_PENDING` | `verify` note, `witness status` (`rotationPending`) | a witness holds the head of a prepared rotation the file does not hold yet (a crash between the witness's acceptance and the local append). Not a rollback | any owner command appends it (§7.1) |
| `REMOTE_WITNESS_ROTATION_INCOMPLETE`; `rotationIncomplete` | `verify` note, `witness status` (`ROTATION INCOMPLETE`, JSON `pendingKeyEvents`), `owner rotate-key` result | a bound witness has not recorded an owner key rotation: until it does, it still accepts head statements signed by the retired key | `irontrellis witness sync`; if the witness stays unreachable, hand its operator the bundle (`irontrellis owner export-key-events`, §7.3). Keep the retired key file (§7.6) |
| `REMOTE_WITNESS_SUPERSEDED n` | `verify` note, `witness status`; a WARNING in the CLI output | the witness recorded `n` supersedes: heads an owner key signed after the last good head were overridden by the owner's pre-rotated rotation (§7.4) | §6.3: the old key was probably compromised. Keep the next key offline, check the agent host |
| `ROLLBACK_DETECTED` with `detail.supersede` | owner write, `witness sync` | a witness holds heads that conflict with the file, and the client could not supersede them: the rotation is not pre-rotated, no last good head is known, the old key is missing, or the witness refused (the reason is in `detail.supersede`) | §6.2; with a stolen key and no commitment the witness's copy stays until a successor history (docs/OPERATOR.md §4) |
| `NO_NEXT_KEY_COMMITMENT` | `verify` note, `witness status`, `owner status` | the owner keys in force have no next-key commitment, so a leaked current key can rotate and no supersede is possible (§3) | `irontrellis owner commit-next-key` and keep the next key off the host |

### 6.2 Recovering from a detected rollback

<!-- source: WITNESS.md:303-303; exact text except relative Markdown links -->

   This works only when the witness's own verified answer shows that this copy lacks a head it holds (`WITNESS_AHEAD` or `WITNESS_FORK`, from a verified network answer in this process, never from the side file, so nothing on disk can fake it), and only with the owner key in force (`KEY_UNAVAILABLE` otherwise): an attacker without the key gains nothing from it. It opens the history despite that witness's finding, writes an owner-signed `WITNESSES_UNBOUND` whose data records the reason and the heads the witness holds (`acceptedLoss`), clears that witness's alarm and removes it from the policy. Any other witness still applies, and the unbinding itself is refused while another witness shows a rollback: when several witnesses hold the lost heads (the usual case: they all received them), name them together (`witness remove <url1> <url2> --accept-loss --reason …`). What it means: the history continues on a branch the removed witnesses never saw; the events they hold past it are gone from the history; they will never accept a head of the new branch (so they cannot be added back: `witness add` refuses with `ROLLBACK_DETECTED`); copies from before the unbinding still name them and fail against them. Add a new witness (`irontrellis witness add`) to protect the history from here on, and re-create any grants or revocations the lost events held. A successor history (docs/OPERATOR.md §4) remains the alternative when you would rather not continue the old one.

## 7. Owner key rotation with a witness

`irontrellis owner rotate-key` (API `owner.rotateOwnerKey()`) records `OWNER_KEYS_ROTATED` at position `r`, signed by the current key; the new key set governs from `r + 1`, and the head at `r` is still attested under the old set (docs/HISTORY-FORMAT.md §7.1). With a next-key commitment (the `init` default), the rotation reveals the committed key with its proof of possession and commits to the next one (docs/HISTORY-FORMAT.md §7.2).

<!-- source: WITNESS.md:334-358; exact text except relative Markdown links -->

### 7.1 The two-phase rotation (the default with bound witnesses)

When the history binds remote witnesses, `rotateOwnerKey` (without `emergency`) runs in two phases:

1. **Flush.** The queue is flushed, and every bound witness must then have answered, in this process, with exactly the local head `r − 1` as its latest. Otherwise nothing is prepared: `WITNESS_UNAVAILABLE`, reason `ROTATION_NEEDS_WITNESSES`, message *rotation needs every bound witness; retry, or rotate with --emergency*.
2. **Prepare, under the writer lock.** The rotation is built and signed in memory (fixed event id and timestamp), its key files are staged (`<history>.owner-key.pending.json`, `<history>.owner-next-key.pending.json`), head `r` is computed with the history hasher, the statement for `r` (previous `r − 1`) is signed with the **old** key, and the **prepared-rotation record** `<history>.rotation.pending.json` is written (0600, atomically; docs/HISTORY-FORMAT.md, side files).
3. **Deliver, still under the lock.** One `POST /v1/histories/:id/key-events` per bound witness carries the rotation and the statement for its head (§9.2): the witness appends `HEAD r` (old key) and `ROTATED` together. A lost answer is asked again (`GET /v1/histories/:id`): a witness whose latest is now `r` accepted it, one still at `r − 1` did not.
4. **Commit or abort.**
   * Every bound witness accepted: the exact prepared event is appended locally (the recorded head must equal `r`), the key files are swapped, the record is cleared.
   * Some accepted, some did not (they refused, or their outcome stays unknown): the rotation is appended anyway (a witness already holds `r`), and the rest get it from the queue (and the bundle, §7.3). This is the **rotation incomplete** state: `rotateOwnerKey` returns `rotationIncomplete: true`, `witness status` shows it (`rotationIncomplete`, `ROTATION INCOMPLETE`), and `verify` notes `REMOTE_WITNESS_ROTATION_INCOMPLETE` for each witness that lacks it (JSON `pendingKeyEvents`).
   * None accepted and every refusal is definite: **abort**. Nothing is appended, the staged key files and the record are removed, and the call throws `WITNESS_UNAVAILABLE`, reason `ROTATION_ABORTED`, *rotation needs every bound witness; retry, or rotate with --emergency*.
   * None accepted, and for some witness the outcome is unknown: the record and the staged key files are **kept** (reason `ROTATION_OUTCOME_UNKNOWN`), and every write waits until an owner command resolves it (below).
5. **Deliver the rest** from the queue, and write the rotation's key-event bundle `<history>.key-event-<r>.bundle.json` (§7.3).

**Recovery.** A prepared record is resolved on the next open (locally) or the next owner command (with the witnesses): while it is outstanding (the file's head is still `r − 1`), writes refuse with `WITNESS_UNAVAILABLE`, reason `ROTATION_PENDING`; an owner command (any write, `witness sync`, `owner rotate-key`) asks the witnesses; one that holds `r` makes the store append the prepared event (never a rollback alarm, and without a new owner attestation of the pinned head: the recovery signs nothing); when every bound witness answered and none holds `r`, the record is discarded and its staged key files are removed; a record whose rotation is already in the file is simply cleared and the key files swapped. `verify` reports a witness that holds the head of an outstanding prepared rotation as a note, `REMOTE_WITNESS_ROTATION_PENDING`, not as a rollback. `owner rotate-key --emergency` with an outstanding record whose outcome is unknown records that prepared rotation now (only when its staged new owner key, or the signer given, holds the record's key). Each crash point, with one test each (`packages/core/test/two-phase-rotation.test.mjs`, fault points `after-stage` … `after-owner-key-swap`; the real-server e2e `packages/witness/test/e2e-prerotation.test.mjs` (f) repeats the third). After the last one the record is gone and a witness that did not accept gets the rotation from the queue ("rotation incomplete" until then):

| crash after | on disk | at the witnesses | recovered by | result |
|---|---|---|---|---|
| staging the key files | staged key files, no record | `r − 1` | the next open or rotation (settle) | staged files removed (no epoch declares their keys); nothing recorded |
| writing the record | record + staged files | `r − 1` | the next owner command | every bound witness answers `r − 1`: record discarded, staged files removed; writes continue |
| a witness accepted (file still at `r − 1`) | record + staged files | `r` (+ `ROTATED`) at one or more | the next owner command (or `verify` shows `REMOTE_WITNESS_ROTATION_PENDING`) | the prepared event is appended (checked like any append, no new attestation), keys swapped, record cleared; **no rollback alarm** |
| the local append | rotation at `r`, record, staged files | `r` at some | the next open (settle) | record cleared, key files swapped; the queue delivers to the rest |
| swapping the owner key file | owner key in place, staged next key | `r` at some | the next open (settle) | next key moved into place |

**The record is attacker-writable, and safe.** It is judged only against the file: it counts (OUTSTANDING) only when the file's head is exactly its `previousHead`, its event passes every replay rule there (owner signature included) and produces exactly its head, its statement is a valid old-key statement for that head, and its seal (the old owner key over every field) verifies. It is completed only when a bound witness's fresh, verified answer holds exactly its head, only through the normal validated append, and only when the key files it staged still hold its keys. Paths are never taken from it. So a planted or edited record never makes the owner sign anything, never lets in an event the replay rules reject, and never rotates the history to a key nobody holds; the most it can do is make writes wait until an owner process asks the witnesses (a garbage or obsolete record does not even do that). A copy of an **aborted** record replayed to a witness still at `r − 1` is the one case that ends in an alarm (§3, a leaked key and a witness that has not recorded its rotation): the recovery refuses to complete it without its staged key files and raises `ROLLBACK_DETECTED`, naming the missing staged key.

### 7.2 Emergency rotation

`irontrellis owner rotate-key --emergency` (API `rotateOwnerKey({ emergency: true })`) records the rotation locally first and delivers it afterwards, to every witness right away (whatever the mode) and first in the queue for any it could not reach, plus the key-event bundle (§7.3). Use it when the key must be replaced now and a bound witness is down (a leak is exactly that case). Until a witness records the rotation, the retired key still counts there; if the rotation is **pre-rotated** (the history has a commitment, which `init` makes), the owner's delivery then supersedes anything the retired key pushed there meanwhile (§7.4). The same applies to a history without bound witnesses (only side-file witnesses), which always rotates this way.

With a witness connected, the old-key statement for head `r` is signed inside `rotateOwnerKey`, while the old key is held, for every witness whose latest this process has verified, and kept in the side file with the rotation; the client never skips head `r` (batching stops at it until the rotation is recorded), and a witness that answers a new-key statement with `SIGNATURE_INVALID` and hint `ROTATION_REQUIRED` gets the pending rotations first.

### 7.3 Out-of-band delivery: key-event bundles

Every rotation (a commitment-only rotation included) writes a self-authenticating **key-event bundle** `<history>.key-event-<position>.bundle.json` (§9.9): the event, the heads around it, the statement for its head (signed by the key in force there, previous = the head before it) and, for a pre-rotated rotation, a `chain` from the last head the owner knew a bound witness held (for a supersede). `irontrellis owner export-key-events [--since <position>]` (API `exportKeyEvents({ since })`) writes them again. A witness operator imports one without the network path:

* `POST /v1/admin/key-events` with the admin token (`Authorization: Bearer <token>`), the bundle as the body; or
* `irontrellis-witness import-key-events --data <dir> <bundle>…` while the server is stopped (it takes the server lock, like `serve`).

Both run exactly the checks of `POST /v1/histories/:id/key-events`: the token or the lock gate the channel; trust comes from the owner signatures in the bundle. A bundle with a forged or altered statement or event is refused like on the network. The runbook is docs/OPERATOR.md §10.

### 7.4 Supersede: a pre-rotated rotation overrides what the old key signed after the last good head

When the client delivers a pre-rotated rotation (the epoch it leaves has a commitment) and meets a witness whose latest head is not a prefix of the file (a `STALE_PREVIOUS` or `EQUIVOCATION` answer, or a latest that is not a prefix), it does not raise the rollback alarm at once. If the history holds that rotation and the witness has not recorded it, the client takes **L**, the newest head this history knows the witness held on its chain (a verified HEAD receipt from this process, or the witness-signed receipt kept in the side file, `held`), requires L to be a prefix of the file and before `r`, signs the **chain** statement (the old key's statement for `r` with `previous = L`) under the writer lock, and sends the rotation with it. The witness checks that L is a head it holds, that the chain statement verifies with a key in force at `r`, and that the rotation is valid and **pre-rotated** against the commitment it knows (the revealed key's `nextKeyAuthorizations` included). It then appends `SUPERSEDED` (the range of leaves after L's HEAD entry: every head it held there is superseded, stays in the log as evidence and is never latest again; the entry has a fixed size, so no number of heads pushed with the leaked key can make a supersede impossible), resets its latest to L, and appends `HEAD r` (the chain) and `ROTATED`. Statements that state or extend a superseded head are answered 409 `SUPERSEDED` from then on. At most one supersede per epoch transition.

`verify` and `witness status` then show `REMOTE_WITNESS_SUPERSEDED n` and a WARNING: *an owner key signed heads that a later pre-rotated rotation overrode; the old key was probably compromised*. The latest note carries the supersede count (§9.8), and `GET /v1/histories/:id` the newest `SUPERSEDED` receipt (`lastSupersede`).

Fail-closed cases: a rotation that is not pre-rotated, an unknown L (no receipt in the process or the side file), a missing old key (`KEY_UNAVAILABLE`), or a refusal by the witness: the client raises the rollback alarm, with the reason in the message and in `detail.supersede`.

### 7.5 Next-key commitments at the witness

A witness judges a rotation against the commitments it knows, and it learns each with the event that fixes it. Epoch 0's commitment is in the genesis, so the witness knows it from the REGISTERED entry, however late it is registered (`witness add`, the queue). A later commitment is carried by the rotation that opens its epoch: a pre-rotated rotation, or the commitment-only rotation that `commitNextKey` / `owner commit-next-key` records; both reach the witness through `POST /v1/histories/:id/key-events` like any rotation (a `ROTATED` entry), in two-phase mode before the local append. `GET /v1/histories/:id` serves each epoch's `nextKeyDigests`.

### 7.6 Keep the retired key file until every witness has the rotation

What the witness records: the `ROTATED` leaf carries the rotation event verbatim, `previousHead` and `rotationHead`, so anyone with the log can check that the rotation was signed by the key then in force, from the leaf alone (`check-log` does). Statements of older heads by the retired key stay valid; a statement of a later head by the retired key is rejected with `SIGNATURE_INVALID` (without the hint, since posting rotations would not help).

If the rotating process had not verified a witness's latest head (the witness was unreachable, or added later), the statement for head `r` has to be signed afterwards, and the only key that can sign it is the retired one: the client loads `<history>.owner-key.<keyId>.retired.json` for that (and signs a supersede's chain with it). Without it, `witness sync` fails with `KEY_UNAVAILABLE`, the witness never learns the new key, and owner writes stop at `maxUnwitnessedEvents`. The same holds for a witness added **after** a rotation: it must be brought through every rotation head, each signed by the key it retired. So:

<!-- source: WITNESS.md:396-396; exact text except relative Markdown links -->

* keep each retired key file offline, encrypted and backed up rather than destroying it, until every witness bound to the history has recorded the rotation (`irontrellis witness status` shows `rotations` per witness: `recorded`, or `PENDING` while the retired key is still needed; JSON `pendingRotations`), and bring it back beside the history for a `witness add` or a `witness sync` that needs it (`irontrellis owner rotate-key` says the same). A witness added later needs it too, so for a history that may get more witnesses, keep it for as long as that may happen. The client finds an archived key file by its key id and public key, whatever its name (`<history>.owner-key.<id>.retired.json`, or with a `-2`, `-3` … suffix when that name was taken), so restore it under any name of that form;
