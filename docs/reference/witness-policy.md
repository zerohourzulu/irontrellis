## 5. Connecting a history

### 5.1 The command

```sh
irontrellis witness add https://witness.example.com --verifier-key 'witness.example.com+1a2b3c4d+AX…' --token itw_…
irontrellis witness status
```

**At creation (recommended).** `irontrellis init --witness <url> --verifier-key <key> [--token <token>] [--mode sync|async] [--require-on-open] [--allow-insecure-http]` registers the genesis with the witness **before the history file exists**, then writes the genesis, the principal and the binding (position 2) together, so the first pinned head already covers the binding and no copy of the history exists without it. A witness that refuses the registration (a missing or wrong token: 401 `UNAUTHORIZED`; 400 `INVALID_GENESIS` / `UNSUPPORTED_FORMAT`), serves another key or answers something that does not verify fails the command with `WITNESS_REJECTED`, and nothing is created (not even the key file). A witness that cannot be reached is bound anyway and registered by the first submission. API: `createLocalOwner({ …, witness: { witnesses: [{ url, verifierKey, token? }], mode: "sync" } })`, same behavior.

**Later.** `witness add <url> --verifier-key <key>` (a format-2 history; needs the owner key or its signer) checks everything the witness will have to accept **before anything is written**: that it serves that verifier key (`GET /v1/witness`), that it registers the genesis, that the head it may already hold for the history is a prefix of this copy (`ROLLBACK_DETECTED` otherwise), and that every head statement it still needs can be signed (the statement for each owner key rotation it has not recorded needs the key that rotation retired, §7: `KEY_UNAVAILABLE` names the positions when a retired key file is missing). Then it writes the policy to `<history>.witness.json`, brings the witnesses up to the head, records an owner-signed binding carrying the witness's signed REGISTERED receipt (§5.3) and submits the head. Failures write nothing: `WITNESS_REJECTED` (a refusal, another key, an invalid answer), `KEY_UNAVAILABLE`, `ROLLBACK_DETECTED`, `WITNESS_UNAVAILABLE` (the witness cannot be reached). Only for the last, `--allow-offline` binds it anyway, without a registration receipt: the queue registers it when it answers. Until `witness add` is run again to record the receipt, the binding is flagged (`REMOTE_WITNESS_BINDING_WITHOUT_RECEIPT`), and readers treat its "not registered" answers as unreachable (§3). Options: `--name <name>`, `--token <token>` (the registration token; kept in the side file, mode 0600), `--timeout-ms <ms>` (per request, default 10000), `--allow-insecure-http` (§4.3), and the policy options below. Adding a second witness later extends the policy; running `witness add` again for a witness with a new token is how a refused registration is fixed. **Moving a bound witness** to a new URL is `witness add <new-url> --verifier-key <same key>`: a new owner-signed `WITNESSES_BOUND` for that key re-binds it in place (editing the URL in the side file does nothing: the binding pins it, §5.3). The policy options given to `witness add` (`--quorum`, `--require-on-open`, `--max-unwitnessed`) are also signed into the binding as its **policy minimum** (§5.3); running `witness add` again with other values writes a new binding that changes it.

`witness remove <url|verifier-key>...` records an owner-signed unbinding (for the witnesses the history binds) and removes them from the policy; copies of the history from before the unbinding still name them, and the witnesses keep what they received. It is an owner write, refused while any witness shows a rollback; `--accept-loss --reason <text>` is the owner's way out of a real loss (§6.2). A witness named by the out-of-band minimum policy (§5.4) cannot be removed here. `witness sync` submits queued statements and rotations now (needs the owner key; exit 1 while they stay queued). `witness status [--no-remote]` shows the policy, the queue, the number of owner key rotations and, per witness, the latest witnessed head, whether its receipt verifies, whether its checkpoint is consistent with the one remembered, how many events it does not hold yet, **whether it has recorded every owner key rotation** (`pendingRotations`: `0` recorded, `n` still pending, `null` not asked), a refused registration (`WITNESS_REJECTED`) and a denied one; it exits 1 on a rollback, a split view, an invalid answer or a refused registration.

From the API: `owner.addWitness(config, update?, { allowOffline? })` and `owner.removeWitness(urlOrKey | urlsOrKeys, { acceptRemoteLoss?, reason? })` do what the commands do (docs/API.md §7a). The hooks and the gateway need no configuration: they open the history through the core, which reads the side file, the history's bindings and the out-of-band minimum policy.

### 5.2 The policy

The options marked *signed* are also recorded, owner-signed, in the binding as the history's policy minimum (§5.3): the effective policy is the strictest of that minimum, the out-of-band minimum (§5.4), the side file and the caller's options, so nothing on the host can lower them.

| option (CLI / API) | default | meaning |
|---|---|---|
| `--mode sync\|async` / `mode` | `async` | when an owner write submits its head statement: `sync` before the write returns, `async` from a background worker that coalesces to the newest head and retries with exponential backoff and jitter (capped at 30 s, 20 attempts, then again on the next write or `flush()`). The CLI and the hooks submit before they exit in either mode |
| `--quorum <n>` / `quorum` (*signed*) | 1 | a head counts as witnessed once `n` witnesses hold it. Every check (the first write of a process, `requireOnOpen`, `verify`, each submission round) needs answers from `witnesses − quorum + 1` of them, so it meets at least one of any `quorum` witnesses that accepted the latest head. With three witnesses, quorum 2 tolerates one witness down, quorum 3 tolerates none, quorum 1 needs all three to answer every check. Rollback or split-view evidence from **any** witness is fatal whatever the quorum |
| `--max-unwitnessed <n>` / `maxUnwitnessedEvents` (*signed*) | 1000 | owner-keyed writers refuse (`WITNESS_UNAVAILABLE`, reason `MAX_UNWITNESSED`) while this many events are not held by a quorum; reads continue. Writers without the owner key sign no statements and are not limited; the next owner-keyed write covers their events |
| `--require-on-open` / `requireOnOpen` (*signed*) | false | readers confirm with the witnesses before they read (`WITNESS_UNAVAILABLE`, reason `NOT_CHECKED`, until a check succeeds; the CLI, hooks and gateway run the check). Owner-keyed writers always check before their first write in a process, whatever this says |
| `--cache-ms <ms>` / `cacheMs` | 60000 | how long a `requireOnOpen` reader may rely on an earlier answer (this process's, or an owner-sealed one in the side file, §3) instead of asking again |

### 5.3 Bindings and the side file

A **binding** is an owner-signed `WITNESSES_BOUND` event `{ witnesses: [{ url, verifierKey, name?, allowInsecureHttp?, registration? }], policy }`, and an unbinding a `WITNESSES_UNBOUND` event `{ verifierKeys, policy, acceptedLoss? }` (docs/HISTORY-FORMAT.md §10.1). The witnesses the history binds are in force whatever the side file says, and every copy of the history from the binding on carries them.

**A bound witness is pinned.** Its URL, verifier key and `allowInsecureHttp` come from the binding **only**. The side file may add a registration token (and a display name) for it; a caller's explicit options may add a timeout and a transport; the out-of-band minimum (§5.4) a token and a timeout. None of them can point the verifier key at another URL (a relay that could answer for it), give it a timeout it cannot meet, or leave it out: a side-file entry with the bound key and another URL is simply ignored. Moving it takes an owner-signed re-binding (`witness add` with the new URL, §5.1).

**The policy minimum.** Every binding and unbinding event carries `policy: { quorum, requireOnOpen, maxUnwitnessedEvents }`, signed with it; the newest one is in force (`boundPolicyOf`). `quorum` is counted over the bound witnesses only (at most their number). The effective policy is the strictest of that minimum, `IRONTRELLIS_WITNESS_POLICY`, the side file and the caller's options: the higher quorum, `requireOnOpen` if any says so, the lower `maxUnwitnessedEvents`. Lowering it takes the owner key (a new binding: `witness add` with the new values; `witness remove` signs the remaining witnesses' minimum). `witness status` shows it (`boundPolicy`, "signed minimum").

**Every bound witness is consulted.** A check (the first owner write of a process, the `requireOnOpen` gate, `verify`, each submission round) needs its answers from each trusted set on its own: from the bound witnesses `bound − boundQuorum + 1` answers (so with the default bound quorum 1, every bound witness must answer), from the out-of-band minimum's witnesses the same with its quorum, and from the whole policy `n − quorum + 1`. Each reachable witness's verified answer must show no rollback (any single one is fatal). Unreachable bound witnesses are handled by the availability policy (§3) within the bound set; a witness added only by the side file can add failures but never substitutes for a bound witness's answer. Raising the side file's `quorum` or adding witnesses to it therefore only makes checks stricter. A `WITNESSES_BOUND` normally carries, per witness, `registration`: the witness's own signed receipt (§9.5) of the `REGISTERED` leaf of this history. A witness that later answers "not registered" contradicts that signature (§6.1). A `WITNESSES_UNBOUND` that accepts a loss carries `acceptedLoss: { reason, heads: [{ verifierKey, head }] }` (§6.2). Replay validates both events in both engines, registration receipts included (docs/HISTORY-FORMAT.md §10.1); the Python verifier, which does not contact witnesses, reports the bound witnesses and, via `bound_policy_of`, the policy minimum.

The **side file** `<history>.witness.json` (0600, written atomically under `<history>.witness.json.lock`) holds the policy (including tokens), the last checkpoint accepted from each witness origin, the last witness answers (optionally sealed with the owner key), a recorded split view, and the queue of pending statements and rotations. It is writable by whoever can write the history, so it may only make things stricter (its policy is merged under the binding's pinning and minimum, above): a deleted or rolled-back side file loses queued items (re-derivable from the history and the witnesses, except as §7 says) and split-view detection strength, never a rollback check; a malformed one fails the open with `WITNESS_UNREADABLE` (reason `WITNESS_STATE_UNREADABLE`) rather than being ignored. It also records a refused registration for `witness status` in processes that never register (display only, and only for the exact witness config that was refused). Back it up with the history; it holds no private keys, but it does hold registration tokens (the gateway's `snapshot` strips them from its copy).

### 5.4 An out-of-band minimum policy (`IRONTRELLIS_WITNESS_POLICY`)

The side file and the history are on the agent host. For a policy the agent cannot touch at all, write a witness policy file somewhere the agent's OS user cannot write (for example `/etc/irontrellis/irontrellis-witness-policy.json`, owned by root or the operator, mode 0600 or 0644, in a directory the agent cannot write either) and set `IRONTRELLIS_WITNESS_POLICY=<absolute path>` in the environment of every IronTrellis process: the CLI, the hook command in the agent host's hook configuration, the gateway's service unit. The file is a `WitnessPolicy` in JSON:

```json
{ "witnesses": [{ "url": "https://witness.example.com", "verifierKey": "witness.example.com+1a2b3c4d+AX…", "token": "itw_…" }],
  "requireOnOpen": true, "maxUnwitnessedEvents": 100 }
```

Every store open of a witnessable (format-1 or format-2) history merges it into the history's policy as a **minimum**: its witnesses are added (its spelling of a witness the policy already has wins), and the fields it states only raise requirements (`quorum` the higher, `mode` `sync` if either says so, `requireOnOpen` if either says so, `maxUnwitnessedEvents` and `cacheMs` the lower); fields it does not state constrain nothing. Nothing on the agent host can lower it: the side file cannot remove its witnesses and `witness remove` refuses them. `createLocalOwner` / `init` register and bind its witnesses too. A copy restored from before a binding is then still checked against them, which closes the residual of §3 for histories bound after creation. A variable that names an unusable file (a relative path, unreadable, not JSON, an invalid policy, writable by group or others) fails every open with `WITNESS_UNREADABLE` (reason `WITNESS_POLICY_UNREADABLE`): an operator's minimum is never dropped silently. Only a caller that passes `witness: false` explicitly (an inspection) opens without it. The hook's protect rules deny tool calls that name `IRONTRELLIS_WITNESS_POLICY`, `irontrellis-witness-policy` or the file the hook's own variable points at; like every protect rule that is a tripwire, not a boundary: the boundary is that the agent's OS user cannot write the file or change the hook's environment.

* **The `requireOnOpen` cache window.** A `requireOnOpen` reader may skip the network when it holds a fresh enough answer: one this process verified within `cacheMs` (at least one second), or one an owner-keyed process sealed with the owner key in the side file, no older than `cacheMs` (default 60 000 ms). A copy restored together with a side file holding such a sealed answer is read for at most that long. Unsealed or forged cached answers never skip the check. A seal (`irontrellis-witness-cache/1`) signs the witness it was made for: the history, the witness's checkpoint origin, its verifier key and the URL it was asked at, plus the head and the time. So a seal copied, relabeled or moved onto another witness's entry is not accepted, and the reader asks the network. Seals are written and accepted only for witnesses the history binds and those of the out-of-band minimum (§5.4), never for a witness only the side file names. For a bound witness, the origin comes from the verified registration receipt in its binding, never from the side file. A witness bound without a receipt (`--allow-offline`) gets no sealed-cache shortcut at all.
* **Asynchronous signers seal after the fact, and only when writing.** A signer without `signHashSync` (a KMS or HSM `Signer`, an ssh-agent or command key reference, docs/CUSTODY.md) seals a cached answer after the side-file update, in a submission round (an owner write, `flush()`, `witness sync`) or a rotation's delivery: the seal is written, under the side-file lock, only while the entry still holds exactly that answer unsealed, and owner writes wait for it. A process that only reads (a hook deciding a tool call, `verify`) never asks such a signer for a seal, since each request could be a person's approval or a hardware touch; it keeps a seal already there for the same answer, and a fresh answer it records is unsealed until the next owner write. A seal the signer fails to give leaves the answer unsealed. Unsealed answers make `requireOnOpen` readers ask the network: this costs latency, not safety.
* **Sync mode reports a rollback after the local append.** In `mode: "sync"` the head statement is submitted after the event is appended locally; if the witness then shows a rollback, the write call throws `ROLLBACK_DETECTED` but the event is already in the file (on the rolled-back copy, and never witnessed). An unreachable witness in sync mode does not fail the write: the statement stays queued.
