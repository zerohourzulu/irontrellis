## A. Keccak-256

### A.1 Variant

The engine implements **original Keccak-256** (the Ethereum variant), not FIPS-202
SHA3-256:

* Keccak-f[1600], 24 rounds, standard round constants generated by the LFSR in
  `host-intrinsics.ts` lines 258–289 (`KECCAK_IOTA_*`), standard rho offsets
  (`KECCAK_ROTL`) and pi permutation (`KECCAK_PI`).
* Rate 136 bytes (`KECCAK_256_RATE = 136`), capacity 512 bits.
* Padding is `pad10*1` with **domain byte `0x01`**: XOR `0x01` into the byte at the
  current position and XOR `0x80` into byte 135 (the last byte of the rate), then
  permute once. SHA3 would use `0x06`; the engine uses `0x01`. When position is
  135 both bytes coincide and the byte becomes `0x81`; when position is 0 (the
  previous block was exactly full and already permuted) the `0x01` goes to byte 0
  of a fresh block. Both are standard.
* Output: the first 32 bytes of the state after the final permutation.

Cross-checked against `@noble/hashes` `keccak_256` for the empty string,
`"abc"`, the 43-byte fox sentence, and byte patterns of length 135, 136, 137, 271,
272, 273 and 1024 (all equal). `keccak256("") = 0xc5d2…a470`, the well-known
Ethereum empty hash.

### A.2 Byte-level state semantics

The state is 25 64-bit lanes stored as 50 JavaScript 32-bit integers in a
null-prototype table `words[0..49]`; lane `i` is `words[2i]` (low 32 bits) and
`words[2i+1]` (high 32 bits). Absorption is byte-by-byte:

```
for each input byte b at absolute stream position p (mod 136):
    words[p >>> 2] ^= b << ((p & 3) * 8)      // little-endian within the 32-bit word
    p += 1
    if p == 136: keccakPermutation(words); p = 0
```

This is exactly the standard little-endian lane loading (byte j of the rate block
lands in lane `j >> 3`, bit offset `8 * (j & 7)`). Output bytes are read back the
same way: byte `k` of the digest is `(words[k >>> 2] >>> ((k & 3) * 8)) & 0xff`
for `k = 0..31`.

Digest formatting: `"0x"` + 64 lowercase hex characters, each byte
zero-padded to two digits (`numberToString(byte,16).padStart(2,"0")`). The engine
never emits uppercase hashes and its validators reject uppercase hashes
(`isContentHash`, schema `contentHash`).

### A.3 The incremental API (needed to reproduce prefix hashing)

Exported from `host-intrinsics.ts`:

| Function | Semantics |
|---|---|
| `createKeccak256State()` | New empty state: 50 zero words, position 0. Returned handle is an opaque frozen object; the data lives in a module-private `WeakMap`, so foreign objects cannot be passed in. |
| `updateKeccak256State(state, bytes)` | Absorbs every byte of the `Uint8Array` as in A.2, permuting whenever 136 bytes have been absorbed. Mutates `state`, returns it. |
| `cloneKeccak256State(state)` | Returns a new independent handle with a copy of all 50 words and the exact position. Subsequent updates to either do not affect the other. |
| `finalizeKeccak256State(state)` | Copies the words and position, applies the padding of A.1 to the **copy**, permutes the copy, and returns the digest. The original state is **not** modified: finalize is repeatable, and further `update`s continue the same stream. |
| `keccak256Bytes(bytes)` | `create` → `update` → `finalize` (one-shot). |

Consequences that a re-implementation must preserve:

* `finalize(S)` twice gives the same digest; `update(S, x)` after `finalize(S)`
  then `finalize(S)` equals `keccak256(absorbed ‖ x)`.
* A clone taken at position `p` after `n` bytes and then finalized equals the
  one-shot hash of those `n` bytes.

Vector (`keccakIncremental` in the JSON): absorb `"The quick brown "`, clone,
finalize → `0x6bb45d609e938d99882098d298caf2ae2f2e49ee24a9e566c96a800632cc09ab`;
absorb `"fox jumps over the lazy dog"`, finalize →
`0x4d741b6f1eb29cb2a9b9911c82f56fa8d73b04959d3d9d222895df6c0b28aa15` (= one-shot
of the 43-byte sentence); finalize the clone → `0x6bb4…09ab` again; absorb `"!"`,
finalize → `0x4ea6eb289d9fde8ccb0163f3b94891fec84196b1e10a18a9ad9114388237a821`.

### A.4 How the engine uses it (`canonical.ts`)

* `hashCanonical(value) = keccak256(UTF-8(canonicalEncode(value)))` — the
  canonical text is `continuity-canonical/0.2` (keys sorted by UTF-8 byte order,
  no whitespace, `undefined` members omitted, BigInt as
  `{"$continuity.bigint":"<decimal>"}`, strings escaped only for `"`, `\` and
  control characters `\u00XX`; see the canonical-encoding spec). Every
  `ContentHash` in a history is produced this way.
* `hashEventHistory(events) = hashCanonical(["continuity-event-history/0.2", events])`.
* `hashEventHistoryPrefixes(events)` produces the head hash of every prefix with
  one continuing state:

  ```
  S = create()
  update(S, UTF8('["continuity-event-history/0.2",['))
  for k in 0..n-1:
      if k > 0: update(S, UTF8(','))
      update(S, UTF8(canonicalEncode(events[k])))
      C = clone(S); update(C, UTF8(']]')); hashes[k] = finalize(C)
  ```

  So `hashes[k] == hashEventHistory(events[0..k])` for every `k` (verified). The
  history head stored in `PortableHistoryHead.hash` at position `k` is `hashes[k]`.
  Events are captured once as a whole wrapper first (bounds/aliasing), then each
  event is canonically encoded individually; the concatenation is byte-identical to
  the one-shot canonical text of the wrapper.

Other `hashCanonical` users that appear in histories (all are plain
`hashCanonical` of the stated value, no extra prefix): adapter policy / profile
descriptor hashes (`portable-adapter-engine.ts`), `derivePortableAdapterIdempotencyKey`,
`submissionFingerprint`, `authorizationProofHash`, `transitionEffectHash`,
`receiptContentHash`, `receiptArtifactCommitment` (§C.2), `termsCommitment`
(`core-0.3 commitTerms`), and `core-0.3` admission ids
`admission:${hashCanonical({declarationId, head})}`.

## B. secp256k1 and EIP-191 "personal sign"

### B.1 Message construction — verified precisely

`portableEip191Digest(contentHash)` (`portable-authority-engine.ts` 3332–3349):

```
preimage = 0x19 ‖ "Ethereum Signed Message:\n32" ‖ raw32(contentHash)      // 28 + 32 = 60 bytes
digest   = keccak256(preimage)
```

* `EIP191_HASH32_PREFIX` is the literal byte array
  `19 45 74 68 65 72 65 75 6d 20 53 69 67 6e 65 64 20 4d 65 73 73 61 67 65 3a 0a 33 32`
  i.e. `"\x19Ethereum Signed Message:\n"` followed by the ASCII decimal length
  **"32"**.
* The message is the **32 raw bytes** decoded from the 64 hex characters of the
  `ContentHash`, **not** the 66-character hex string. Confirmed experimentally:
  `portableEip191Digest(h)` equals `keccak256("\x19Ethereum Signed Message:\n32" + bytes(h))`
  and differs from `keccak256("\x19Ethereum Signed Message:\n66" + utf8(h))`.
* This is exactly what viem's `account.signMessage({ message: { raw: hash } })`
  signs (raw bytes, length 32), which is what every application in the repository
  uses (§D).
* The function throws if the input is not a lowercase `ContentHash`; the nibble
  decoder tolerates uppercase but the regex gate before it does not.

There is no EIP-712 typed-data signing anywhere in the engine. The
`domain` object with `chainId`/`verifyingContract` is a *field of the hashed
structure* (§C), not an EIP-712 domain separator.

### B.2 The signing scheme identifier

The genesis event (`DEPLOYMENT_INITIALIZED.data.versions.signatureScheme`) must be
exactly `"eip191-personal-sign-keccak256"`; replay rejects anything else with
`UNSUPPORTED_VERSION`. Receipts carry the same literal in
`payload.signatureScheme`.

### B.3 Signature encoding and acceptance rules

A signature is a string `"0x"` + 130 lowercase hex characters = `r(32) ‖ s(32) ‖ v(1)`.

Engine-level `isSignature65` (`portable-authority-engine.ts` 465–477), used before
every recovery and for `runtimeSignature` in intent-admission input:

| Check | Rule |
|---|---|
| Syntax | `/^0x[0-9a-f]{130}$/` — **lowercase only**; uppercase or mixed case is rejected |
| `r` | `0 < r < n` (n = secp256k1 order `0xffff…fffebaaedce6af48a03bbfd25e8cd0364141`) |
| `s` | `0 < s <= MAX_LOW_S` where `MAX_LOW_S = 0x7fffffffffffffffffffffffffffffff5d576e7357a4501ddfe92f46681b20a0` (= (n−1)/2). **Low-s is mandatory.** |
| `v` | the last byte must be `1b` (27) or `1c` (28). `00`/`01` (and 35+ EIP-155 values) are rejected. |

Schema-level `signature65` (`event-schema.ts` 416–426), applied to every stored
`runtimeSignature`, `administrativeAuthorization.runtimeSignature` and receipt
artifact `signature`: same syntax, `s != 0`, `s <= MAX_LOW_S`, `v ∈ {1b,1c}`. It
does not check `r < n`, but recovery does, so an `r >= n` signature never verifies.

Recovery id: `v == 0x1b → recovery 0 (even y)`, `v == 0x1c → recovery 1 (odd y)`.
There is no support for `r + n` x-coordinate overflow (recovery ids 2/3); `r` is
used directly as the x-coordinate.

### B.4 Public-key recovery (`recoverPortableContentHashSigner(contentHash, signature)`)

Returns the signer address as a **lowercase** hex string, or `undefined` when the
inputs fail B.3 or the maths fails. Exact algorithm (lines 3495–3542):

```
if !isContentHash(contentHash) || !isSignature65(signature): return undefined
r, s   = parse; rec = (v == 0x1b) ? 0 : 1
e      = portableEip191Digest(contentHash)              // §B.1
y²     = (r³ + 7) mod p
y      = (y²)^((p+1)/4) mod p ; if y·y != y² mod p: return undefined   // r not on curve
if (y is odd) != (rec == 1): y = p − y
R      = (r, y)
z      = e mod n                                        // digest taken as 256-bit big-endian integer
u1     = (n − z) · r⁻¹ mod n
u2     = s · r⁻¹ mod n
Q      = u2·R + u1·G                                    // Jacobian double-and-add, then affine
if Q is infinity or not on curve: return undefined
address = "0x" + hex(keccak256(X(32 bytes BE) ‖ Y(32 bytes BE)))[26..66]   // last 20 bytes
```

i.e. standard ECDSA recovery `Q = r⁻¹(s·R − z·G)`; address = last 20 bytes of
`keccak256(uncompressed public key without the 0x04 prefix)`, rendered lowercase,
no EIP-55 checksum. Any exception inside is swallowed and yields `undefined`.

Any correct secp256k1 library gives the same result for signatures that pass B.3;
the pure-BigInt arithmetic in the repository is not special. (It is, however,
non-constant-time and slow — see §F.)

### B.5 Address comparison

* `RUNTIME_SESSION_ADMITTED.data.credentialAddress` must match
  `/^0x[0-9a-fA-F]{40}$/` — **mixed case is accepted and no EIP-55 checksum is
  validated**. viem stores checksummed addresses (e.g.
  `0x5935897A39AFABbedA5a599D38236E7Df151C8b8` in the fixtures).
* Replay stores `credentialAddressKey = credentialAddress.toLowerCase()` on the
  session record (`portable-replay.ts` 1190, 1222) and enforces per-agent
  uniqueness of that lowercase key and global uniqueness of `credentialKeyId`.
* Every verification compares the lowercase recovered address with either
  `session.credentialAddressKey` (already lowercase) or
  `expectedAddress.toLowerCase()` (`verifyPortableRuntimeAuthorizationSignature`
  accepts a checksummed expected address and lowercases it). Comparison is exact
  string equality after lowercasing; a re-implementation must lowercase both
  sides.
* Domain `verifyingContract` is also compared case-insensitively where two domains
  are compared for *equality* (`sameDomain`, `domainEqual`), but its **spelling is
  hashed verbatim** wherever a domain is part of a signed structure (§C).

## C. Every signature in the system: what is hashed, what is signed, who signs

All signatures are EIP-191 personal-sign (B.1) over a `ContentHash` that is
`hashCanonical` of one specific record. There is **no** other prefix/suffix; the
domain separation is carried inside the record by literal `version` strings and
the `domain` object. The signer is always the **session credential key**: the key
whose address was recorded in `RUNTIME_SESSION_ADMITTED.credentialAddress` for the
session named in the record, and whose `credentialKeyId` is named in the record.

### C.1 Runtime authorization challenge (`TRANSACTION_INTENT_ADMITTED.runtimeSignature`)

Producer: `createPortableRuntimeAuthorizationChallenge(input)` +
`hashPortableRuntimeAuthorizationChallenge(challenge) = hashCanonical(challenge)`.

Record (all fields required; canonical order is by key, shown here in source order):

```
{
  version:              "continuity-runtime-authorization/0.2",
  domain:               { protocol:"continuity", version:"0.2", deploymentId, chainId, verifyingContract },
  request:              { actorId, action, resource, claimedAt, amount?, counterpartyId?, termsCommitment? },
  authoritative:        true,
  consequential:        true,
  evaluationTime:       <u53>,
  policyVersion:        <identifier>,
  rootRecognitionPolicy:"declared-principal-root/0.2",
  eventHistoryHash:     historyHead.hash,
  eventHistoryPosition: historyHead.position,      // canonicalTime is NOT included
  runtimeSessionId, credentialKeyId, controlEpoch, roleId, roleTenureId, intentId, nonce
}
```

* `domain` is copied field-by-field from the caller's `domain` (`normalizedDomain`),
  **preserving the case of `verifyingContract`**. `request` is copied with optional
  members present only if present in the input (`normalizedRequest`). `amount` is a
  BigInt and canonicalizes as `{"$continuity.bigint":"2500"}`.
* `credentialKeyId`, `intentId`, `nonce` are required (throws otherwise).
* `historyHead` is the head of the history **before** the admission event
  (`expectedHistoryHead`, position = index of the last existing event).
* Signed hash: `hashCanonical(challenge)`; stored in the event as
  `data.runtimeAuthorizationHash`; signature stored as `data.runtimeSignature`.

Verification points:

1. **Admission / authorize path** (`stagePortableStateAuthorization`, 4025–4075):
   when `consequential` with a `binding` that has `credentialKeyId`,
   `runtimeSignature`, `intentId` and `nonce`, the engine rebuilds the challenge
   from the caller's `domain`, `request`, `evaluationTime`, `policyVersion`,
   `state.head` and the binding, and requires
   `verifyPortableRuntimeAuthorizationSignature(session.credentialAddressKey, challenge, runtimeSignature)`;
   failure → `DENY SESSION_CREDENTIAL_INVALID`. `credentialKeyId` must equal
   `session.credentialKeyId`. (Missing credential/signature →
   `SESSION_CREDENTIAL_REQUIRED`.)
2. **Replay** of a stored `TRANSACTION_INTENT_ADMITTED`
   (`validatePortableIntentAdmissionTransition`, 4696–4755): the challenge is
   rebuilt from the **stored proof** — `proof.domain`, `proof.request`,
   `proof.evaluationTime`, `proof.policyVersion`, the pre-event `state.head`, and
   the binding `{proof.runtimeSessionId, proof.credentialKeyId, proof.controlEpoch,
   proof.roleId, proof.roleTenureId, proof.intentId, proof.nonce}`. It requires
   `data.runtimeAuthorizationHash === hashCanonical(challenge)`, then
   recovers the signer of `(runtimeAuthorizationHash, data.runtimeSignature)` and
   requires it to equal `session.credentialAddressKey` for
   `proof.runtimeSessionId`, plus `session.credentialKeyId === proof.credentialKeyId`
   and `session.agentId === proof.request.actorId`'s agent. Also
   `event.timestamp === data.evaluationTime === proof.evaluationTime`, both heads
   equal `state.head`. Any failure → `TRANSITION_INVALID` for the whole history.

Hash-relevant subtleties: the domain hashed is the one **stored in the proof**
(which was the caller's spelling at admission), so a checksummed
`verifyingContract` supplied at admission stays checksummed in the proof and in the
challenge; `sameDomain` only compares it case-insensitively against genesis.

### C.2 Receipts (`createPortableReceipt` / `verifyPortableReceipt`)

Payload (`PortableReceiptPayload`, built at `portable-receipts.ts` 403–416):

```
{
  schemaVersion:  "continuity-receipt/0.2",
  signatureScheme:"eip191-personal-sign-keccak256",
  domain:         proof.domain,                       // from the stored admission proof
  issuer:         { keyId: admission.credentialKeyId, agentId, runtimeSessionId, controlEpoch, roleId, roleTenureId },
  intent:         <TRANSACTION_INTENT_DECLARED.data of the intent>,
  authorization:  { authorizationTime: proof.evaluationTime, policyVersion, rootRecognitionPolicy, historyHead: proof.historyHead, proof },
  issuance:       { historyHead: <head of the events given to createPortableReceipt>, issuedAt },
  result:         { status:"SUBMITTED", consumptionEventId, adapterId, idempotencyKey, submissionFingerprint, transactionReference, acknowledgment },
  assurance:      { finality:"LOCAL_ONLY", freshness:"CURRENT_AT_ISSUANCE", externalOutcome:"NOT_PROVEN"|"SIMULATED" }
}
```

* `contentHash = hashCanonical(payload)`; `signature = await signer.signHash(contentHash)`
  (signer `keyId` must equal `admission.credentialKeyId`). Artifact =
  `{ payload, contentHash, signature }`.
* The producer then runs `verifyPortableReceipt` on its own artifact and throws if
  `historical` is false, so a bad signer never yields an artifact.
* `receiptArtifactCommitment = hashCanonical(["continuity-receipt-artifact-commitment/0.2", contentHash, signature])`
  (`portable-receipt-codec.ts` 170–197). The `RECEIPT_RECORDED` event stores only
  `receiptContentHash`, `receiptArtifactCommitment`, `intentId`, `issuerAgentId`,
  `runtimeSessionId`, `controlEpoch`, `roleId`, `roleTenureId`,
  `authorizationProofHash = hashCanonical(payload.authorization.proof)`.
  **Replay of `RECEIPT_RECORDED` performs no signature check** (only referential
  existence, `portable-replay.ts` 1935–1956); the artifact itself is not in the
  history. The signature is verified at record time (`proposePortableReceiptRecord`
  requires `verification.current`) and whenever someone presents the artifact.
* `verifyPortableReceipt` axes tied to crypto:
  `contentIntegrity` = `hashCanonical(payload) === artifact.contentHash`;
  `signaturePossession` = `recoverPortableContentHashSigner(contentHash, signature) !== undefined`
  (any valid low-s signature by anybody passes this axis);
  `issuerAuthentication` = the recovered address equals
  `session.credentialAddressKey` of `old.runtimeSessions.get(payload.issuer.runtimeSessionId)`
  where `old` is the replay of the issuance prefix `issuanceEvents[0..issuance.historyHead.position]`,
  and `session.agentId === issuer.agentId`, `session.credentialKeyId === issuer.keyId`.
  `authentic = integrity && recovered !== undefined && issuerAuthentication PASS`.

### C.3 Administrative authorization (OBLIGATION_CREATED, OBLIGATION_PERFORMANCE_ASSIGNED, OBLIGATION_STATUS_RECORDED, OUTCOME_OBSERVATION_RECORDED, ATTEMPT_DUTY_CREATED/ASSIGNED/REVIEW_CLOSED)

Stored in `event.data.administrativeAuthorization = { challenge, authorityProof, runtimeSignature }`.

Challenge (`PortableAdministrativeAuthorizationChallenge`, built at
`administration/index.ts` 230–251):

```
{
  version:               "continuity-administrative-authorization/0.2",
  domain:                state.genesis.domain,           // EXACT genesis spelling
  request:               requirements.request,           // derived, see below
  authoritative: true, consequential: true,
  evaluationTime:        transition.timestamp,
  policyVersion:         state.genesis.policyVersion,
  rootRecognitionPolicy: state.genesis.rootRecognitionPolicy ("declared-principal-root/0.2"),
  eventHistoryHash:      state.head.hash,                // head BEFORE this event
  eventHistoryPosition:  state.head.position,
  transitionEventId:     transition.id,
  transitionEventType:   transition.type,
  transitionEffectHash:  hashCanonical(portableAdministrativeTransitionEffect(event)),
  runtimeSessionId:      session.id,
  credentialKeyId:       session.credentialKeyId,
  controlEpoch:          session.controlEpoch,
  roleId:                requirements.roleId,
  roleTenureId:          requirements.roleTenureId,
  authorityProofHash:    hashCanonical(authorityProof)
}
signingHash = hashCanonical(challenge); runtimeSignature = await signHash(signingHash)
```

* `transitionEffect` is a projection of the event's own data **without** the
  `administrativeAuthorization` member, with `transitionEventType` added
  (`portable-administration-codec.ts` 158–218). For `OBLIGATION_CREATED` it is
  `{ transitionEventType:"OBLIGATION_CREATED", record: <full obligation record>, actorId }`;
  for `OBLIGATION_PERFORMANCE_ASSIGNED` it is
  `{ transitionEventType, obligationId, fromAgentId, toAgentId, successionRuleId, actorId }`;
  the other five are listed in that file.
* `request` for `OBLIGATION_CREATED`: `{ actorId, action:"OBLIGATE", resource: <source intent's resource>, claimedAt: timestamp, termsCommitment: record.termsCommitment, counterpartyId? (if the record has one) }`;
  for `OBLIGATION_PERFORMANCE_ASSIGNED`: `{ actorId, action:"ASSIGN_PERFORMANCE", resource: obligationId, claimedAt }`;
  for `OBLIGATION_STATUS_RECORDED`: action `"record-collection-disposition"`; the
  E5/E6 attempt-duty events use `OBSERVE_OUTCOME`, `CREATE_ATTEMPT_DUTY`,
  `ASSIGN_ATTEMPT_DUTY`, `CLOSE_ATTEMPT_DUTY` with `resource = intentId`
  (`administration/index.ts` 119–209).
* `authorityProof` is the deterministic non-consequential `PortableAuthorizationProof`
  (`createPortableAdministrativePolicyProof`, domain = genesis domain,
  `historyHead = state.head`, `evaluationTime = timestamp`).

Replay verification (`validatePortableAdministrativeTransition`, 4234–4297) checks,
all with exact equality:
`canonicalEncode(challenge.domain) === canonicalEncode(genesis.domain)` (**case-sensitive**),
same for `proof.domain`; `canonicalEncode(challenge.request) === canonicalEncode(derivedRequest)`;
`challenge.eventHistoryHash/Position === state.head`; `evaluationTime === event.timestamp`;
`transitionEventId === event.id`; `transitionEventType === event.type`;
`transitionEffectHash === hashCanonical(effect(event))`;
`authorityProofHash === hashCanonical(proof)`; role/tenure/session/epoch congruence;
then `recoverPortableContentHashSigner(hashCanonical(challenge), runtimeSignature) === session.credentialAddressKey`
for `challenge.runtimeSessionId`; finally the stored proof must canonically equal a
freshly computed `createPortableAdministrativePolicyProof`.

### C.4 `RUNTIME_SESSION_ADMITTED`

**Not signed.** Its data is `{ sessionId, agentId, controllerId, controlEpoch,
credentialKeyId, credentialAddress, expiresAt? }`. `credentialAddress` is a bare
Ethereum address (checksum not verified) declared by the owner/controller; it is
the public key binding that every later signature is checked against. Nothing
proves possession of the key at admission time; possession is proven by the first
valid `runtimeSignature`. `credentialKeyId` is an opaque identifier (in the tutorial
`key:<case>:<a|b>`, in core-0.3 whatever the application passes as `key`).

### C.5 MCP gateway, core-0.3, remote tools, reference application

* `packages/mcp-gateway/src/cli.mjs` reads a private key file (`0x` + 64 hex,
  mode 0600) and builds `signHash: hash => privateKeyToAccount(key).signMessage({message:{raw:hash}})`
  (viem). It signs nothing of its own; all signing flows through core-0.3
  (`openLocalExecution`, `openLocalRuntime`, `openAttemptRuntime`) which call the
  three producers above. `gateway.mjs`/`cooperative.mjs` wrap `signHash` only to

## D. How applications provide a signing key

Contract (`packages/core-0.3/src/execution.ts` 22; `portable-receipts.ts` 386;
`administration/index.ts` 287–302):

```ts
type SignHash = (hash: ContentHash) => Promise<`0x${string}`>;
```

* Input: one `ContentHash` (`0x` + 64 lowercase hex), already the Keccak-256 of
  canonical text. The callback must **EIP-191 personal-sign the 32 raw bytes** of
  that hash (B.1) — never hash it again, never sign the hex string.
* Output: `0x` + 130 hex = `r ‖ s ‖ v` with `v ∈ {0x1b, 0x1c}` and low-s (B.3).
  Lowercase is required by the schema.
* `createPortableReceipt` takes `{ keyId, signHash }` and requires `keyId ===
  admission.credentialKeyId`. `produceAdministrativeEvent(input, options)` requires
  `options` to be a plain object (`Object.prototype` or null prototype) whose only
  own property is a data property `signHash` that is a function; it is called
  exactly once with `prepared.signingHash`; a throw maps to `SIGN:SIGNER_FAILED`;
  a malformed result maps to `VERIFY:INVALID_SIGNATURE` or `SIGNED_EVENT_REJECTED`
  (the signed event is replayed before being returned).
* The core-0.3 wrapper (`execution.ts` 97–107) maps any throw to
  `ContinuityError("SIGNER_FAILED")` and re-validates the history head after the
  async signing boundary (a stale prefix or expired session between hashing and
  signing aborts the operation).

Key creation in the repository (all **viem 2.55.19**, which uses `@noble/curves`
secp256k1 with RFC 6979 deterministic nonces and low-s normalisation, and
`@noble/hashes` keccak):

* Tests (`tests/core-0.3/*.test.mjs`), `examples/core-0.3/handover.mjs`,
  `packages/mcp-gateway/examples/setup.mjs`: `privateKeyToAccount(generatePrivateKey())`,
  `address = account.address` (EIP-55 checksummed), `signHash = hash => account.signMessage({ message: { raw: hash } })`.
* Tutorial (`tutorial/cli.mjs` → `integrations/core-0.2-reference/src/application.mjs`
  `credentials()`): fixed **public development scalars** — agent `a` uses private
  key `1001` (`0x…03e9`, address `0x5935897A39AFABbedA5a599D38236E7Df151C8b8`) and
  agent `b` uses `1003` (`0x…03eb`, address `0xa78Cac12f68179fd780Ae347F8D4F170FC615D0C`).
  All checked-in fixtures (`tests/fixtures/handover-history.json`, conformance
  vectors, reference cases) are signed with these keys, which is why every fixture
  signature is reproducible byte-for-byte (verified: re-signing with viem gives the
  identical `runtimeSignature` for events 14, 18 and 23 and the identical receipt
  signature).
* `packages/mcp-gateway/src/cli.mjs`: key from a file, same viem call.
* The engine itself never generates keys and never signs; it only hashes and
  recovers. There is no key material in `packages/core-0.2`.

## F. Performance of the repository implementations (Node v22.22.2, single core)

| Operation | Repo implementation | Reference |
|---|---|---|
| Keccak-256 of 1 KiB | ≈ 160–200 µs | `@noble/hashes` ≈ 107 µs |
| Keccak-256 of 64 B | ≈ 30 µs | — |
| Keccak-256 of 1 MiB | ≈ 157 ms | — |
| secp256k1 recovery (`recoverPortableContentHashSigner`) | ≈ 3.3–3.7 ms | viem/noble sign ≈ 0.9 ms |

The recovery is two full 256-bit Jacobian double-and-add multiplications with
BigInt modular arithmetic and no precomputation; a native or noble-based
implementation is 10–50× faster. A 26-event fixture history has three signatures
(one admission, two administrative), so signature verification is ~10 ms per
replay; hashing dominates only for large histories (~4 KB canonical text per
receipt-bearing event ≈ 0.7 ms). None of the repository arithmetic is
constant-time; that is acceptable because only public-key recovery (no secret
material) is performed by the engine.

## G. Checklist for a verifying re-implementation

1. Keccak-256 with `0x01` padding, rate 136, lowercase `0x` hex output; incremental
   state with independent clone and non-destructive finalize.
2. Canonical encoder producing byte-identical `continuity-canonical/0.2` text
   (validate with the `canonicalText` fields in the vectors before touching crypto).
3. History head at position `k` = `keccak256('["continuity-event-history/0.2",[' + join(",", canonical(e_0..e_k)) + "]]")`.
4. Signature parser: lowercase 130-hex, `0<r<n`, `0<s<=(n−1)/2`, `v∈{27,28}`; anything
   else is invalid (not "normalised").
5. EIP-191 digest of the **32 raw bytes** with the `"\n32"` prefix; ECDSA recovery
   to an uncompressed point; address = last 20 bytes of `keccak256(X‖Y)`, lowercase.
6. Compare against `credentialAddress.toLowerCase()` of the session named in the
   signed structure, and require `credentialKeyId` equality as well.
7. Rebuild the three signed records exactly as in C.1–C.3 from replay state
   (pre-event head, stored proof/domain spelling, genesis policy), never from the
   event's own claims alone, and require the stored hash fields
   (`runtimeAuthorizationHash`, `transitionEffectHash`, `authorityProofHash`,
   `contentHash`) to equal the recomputed ones.
8. `RUNTIME_SESSION_ADMITTED` and `RECEIPT_RECORDED` carry no verifiable signature;
   verify receipts only when the artifact is presented.
